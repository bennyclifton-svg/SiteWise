# Trades on Procurement: one RFT format

Date: 8 November 2026. Lane A (procurement packages, issued documents).

## Owner direction (8 November 2026)

- Procurement has two tabs, **Consultants** and **Trades**.
- Most projects have one head contract (Main Works). Some let a few trades
  directly. A trade bought as a supply (for example mechanical equipment) is
  still a trade row and still an **RFT**. No request-for-quote variant and
  no separate supplier document: consultants get an RFP, trades get an RFT.
- Every RFT follows the format of the consultant RFPs: the same page one
  (project table), the same editing controls, the same Before issue
  checks, issue section and Excel response form. Scope of works is custom
  per trade.
- Any consultant RFP still in the old generic layout moves to the new one.

## Why

Trades had a Trades group in the table and a generic RFT, but nothing
proposed a trade, and the RFT used the old generic report layout. Thirty
consultant disciplines with no RFP file (acoustic, heritage, BASIX, ESD,
hazmat and others) fell back to the same old layout. One format means a
project manager learns one document and the price table, award and Program
read every package the same way (time-to-decision, answer trust).

## Design

1. **One engine.** The trade RFT is a discipline file in `knowledge/rfp/`
   with `kind: works`, resolved by `internal/rfp` exactly as a consultant
   RFP. No Jev call anywhere (AGENTS.md: report create and edit do not call
   Jev).
2. **Tender skeleton.** `knowledge/rfp/skeleton-works.yaml` holds what a
   tender changes: fields (contract, site possession, completion, defects
   period, insurances), terms and returnables R1-R9 (tender price, rates,
   program in R7 as for consultants). Lists it omits (flags, pathways,
   procurement routes, work types, project rows) are the consultant
   skeleton's, so page one is identical.
3. **Price rows are the building.** A trade's "stages" are the systems it
   builds, each priced and each mapped to the Delivery project stage, so
   award by stage writes the contract value into Delivery. A row shows when
   the project's Profile scope includes that system (`system` condition);
   with no scope recorded yet it is included on a printed assumption.
   Scope lines are editable and the PM can add their own lines per row.
4. **Carve-out.** A Main Works row names the trade that may be let
   separately (`separate`). When another live package holds that trade,
   the row prints as excluded, by the separate contract. Main Works
   always holds whatever is not let separately.
5. **No old layout.** A consultant discipline with no file uses
   `consultant-general.yaml`; a trade with no file uses
   `trade-general.yaml`. Both print the package title in the heading.
6. **Tabs.** Procurement shows Consultants or Trades, same table, same
   actions. Main Works is proposed on every project that builds (owner:
   most projects have a head contract) and can be dismissed.

## Out of scope

Request for quote, supplier-specific documents, construction-management
fee structures, rates or prices (unknown stays unknown), owner review of
the new knowledge files (all `status: draft`; issue stays blocked until the
owner reviews them, as for every draft discipline).

## Budget

Report create, refresh and settings writes keep the budgets already in
`bench/budgets.json` for report paths. Nothing new runs on a hot path.
