# Unit mix on the Project card

Owner request, 8 Nov 2026: multi-unit residential is usually a mix of one-,
two- and three-bedroom apartments, and the card only holds one Bedrooms
number. On a mixed-use job the documents name several bedroom counts, so the
card shows Bedrooms "2-6, Sources differ", which is noise. Owner approved the
suggested direction and asked for it built without further questions.

## Outcome

A Class 2 or other multi-unit project shows its mix on the Project card: one
count per type (Studio, 1-bed, 2-bed, 3-bed, 4+ bed), each with its own
sources, editable like any other field. The summary sentence and the RFP
project grid print the mix ("14 × 1-bed, 38 × 2-bed, 12 × 3-bed").

Serves answer trust and time-to-decision: the architect, BCA and services
briefs depend on the mix; a single conflicting Bedrooms row helped nobody.

## Lane

A (profile values a user trusts). Existing profile tests and answer keys must
still pass.

## How it works

- Knowledge: five scale fields (`units_studio`, `units_1_bed`, `units_2_bed`,
  `units_3_bed`, `units_4_bed`) on the subclasses that count units or
  dwellings: apartments, BTR, townhouses, and the mixed-use classes with a
  residential component. Triggers gate on the type phrase.
- Code harvests candidates: only a count written against a type phrase
  ("14 one-bedroom", "6 x 2B", "2 Bed: 4", "two-bedroom apartments (38)").
  A bare type phrase ("a 4 bedroom house", "a mix of one, two and three
  bedrooms") gives no candidate, so no question is asked.
- Jev picks among those candidates in the existing label fan-out
  (https://docs.typesafe.ai/patterns/fan-out,
  https://docs.typesafe.ai/cookbooks/pre_parsed_value_extraction_cookbook).
  No new call, no new round trip.
- The API lists mix fields for a subclass that has them, and for an unknown
  subclass when a document states a count. A subclass known not to have them
  never shows them. Where the mix shows, the house Bedrooms row is not
  offered from stray evidence.
- The mix text for the summary and the RFP grid is assembled in code from
  known counts only. Unknown counts are left out, never guessed; no total is
  invented from a partial mix.

## Budget

No new path. Profile read stays at `project_profile_read` in
`bench/budgets.json`; filing stays p50 ≤ 1 s, p90 ≤ 2 s. The added questions
ride an existing fan-out.

## Out of scope

Unit sizes per type, accessible/adaptable counts, a mix editor table, the
total bedrooms figure, cost-plan or program use of the mix.

## Edge cases

- House documents ("4 bedroom home"): no candidate, nothing shown.
- Percent mixes ("40% two-bedroom"): not a count, not a candidate.
- Word numbers ("six two-bedroom apartments") are read.
- A project stating counts for some types only: the others stay unknown.

## Done

Harvest tests for each form above, API listing test, RFP grid row test, the
existing profile and RFP suites, `check_knowledge.py`, and one live Jev read
of a mix passage.
