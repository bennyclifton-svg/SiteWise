## 1. Purpose and scope

Build the Program view: one quick, low-friction program per project, generated from the Profile and the knowledge library, edited like a spreadsheet and a Gantt chart, with every date computed in Go. Jev never computes or invents a date; it only picks among candidates code has found in documents.

**Who it is for.** Project managers during planning and for long-range programming. Detailed construction programs stay in contractors' own tools (Primavera P6, Microsoft Project). Success means the program is fast and easy to manipulate, not that it matches those tools feature for feature.

**User outcome.** A PM creates a project, fills the Profile as far as they can, then opens Program, Procurement or the Cost Plan in whatever order suits them. In Program they see a default program aligned to the Profile within three clicks. They rename any stage or activity in place, add, delete, select many with Ctrl/Cmd-click and Shift-click, drag to reorder and re-sequence, link, and print.

**The model in one paragraph.** One program, two tiers: **stages** (parents) and **activities** (children). Two views: **collapsed** (stages only) and **expanded** (stages with their activities). There are no detail variants and no alternative stage regimes in v1. The program's stages are the project's **stage plan**, shared with Procurement (RFP and package stages) and the Cost Plan (fee lines per stage). Nothing changes silently in either direction: Program edits reach RFPs and contracts as Update or Keep offers, and Profile, Procurement or document changes reach the Program as a review the user adopts or keeps.

**Why this is not a side quest.** It cuts time-to-decision on the question PMs are asked most ("when"), it reuses the building model (stages, packages, work items, `sequences` interfaces, hold points), and it ties Program, Procurement and the Cost Plan to one set of stages.

**Lanes.**

| Part | Lane | Why |
| --- | --- | --- |
| Engine, data, generation, review, API, Jev readings | A, product core | Users will trust these dates. Existing tests, answer keys and budgets must still pass. |
| Stage plan shared with Procurement and Cost Plan | A, product core | Touches package stages, RFPs and fee lines that already carry money. Their tests must still pass. |
| Chart chrome, toolbar, empty states, print styling | B, edge | Move fast; do not break filing. |
| Vitest (dev dependency only) | C | One new dev dependency, justified in the commit message. No new runtime dependency. |

**In scope (v1).**

- Default program generated from Profile facts, included work items, Procurement packages and their stages, `sequences` interfaces with hold points, and reviewed library rows.
- Two tiers only and two views only: collapsed and expanded, per stage or all at once.
- Click-to-rename for every stage and activity; add, delete, reorder, indent and outdent.
- Bulk selection with Ctrl/Cmd-click (toggle) and Shift-click (range), in the grid and the chart; bulk drag, delete, shift and link.
- Reordering stages or activities re-sequences their default chain links.
- Link types FS, SS, FF and SF with lag (positive or negative, working or calendar days), including links between stages.
- Project calendar: working week, public holidays, RDOs and shutdowns.
- Critical path, float, driving links, completion range, plain-language checks (for example consent lapse).
- Fit to screen, fit to selection, fit height; Excel and CSV export; A3 landscape print.
- One stage plan per project, created by whichever of Program, Procurement or Cost Plan needs it first; a stage picker on each Procurement package; Update or Keep offers on RFPs, contracts and fee lines when stages change.
- An ask-first review for anything outside the Program that would change it.
- Three Jev readings, all background: a dropped program file, the R7 Program returnable in proposals, and hold-point release evidence.

**Out of scope (v1).** Switching between alternative stage regimes; more than two tiers; resource levelling, cost loading or cash flow, earned value, baselines, percent-complete tracking and per-activity calendars; MS Project or Primavera import and export; editing stages from Procurement (Procurement only chooses which program stages a package covers). Name these as follow-ups; do not build them.

## 2. Non-negotiable rules for implementers

Breaking any rule below is a failed work package, even if the feature works. When a rule blocks you, stop and report; do not work around it.

### Jev rules

Source: `AGENTS.md` non-negotiables 1–3, `docs/design/2026-09-29-foundation-design.md` §1–2, and `knowledge/SCHEMA.md` "Questions (Jev)". Cite the TypeSafe page in a code comment beside every Jev use.

1. **Jev is the only AI.** No LLM, embedding, chat agent or other model anywhere, including "just to suggest durations" or "just to name activities". Code parses, computes, looks up and controls flow; Jev picks. ([How to build](https://docs.typesafe.ai/concepts/how-to-build-with-system-one))
2. **Jev never does maths, counting, dates or unit conversion.** No durations, date arithmetic, date comparison, sorting by date, critical path, float or "is this enough". Ask whether a value is *stated*, never whether it is right. ([jev-1.13 limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13) §2–3)
3. **Jev never writes text.** Activity names come from the library or are copied verbatim from a document candidate. Never ask Jev to name, summarise or describe. (jev-1.13 §9)
4. **Pre-parsed extraction only.** Code over-finds candidates; Jev picks one candidate or `none`; code copies the selected candidate's source value verbatim. ([Pre-parsed extraction](https://docs.typesafe.ai/cookbooks/pre_parsed_value_extraction_cookbook))
5. **One fan-out per state.** All questions about one document go in one request. Never serial round trips. ([Fan-out](https://docs.typesafe.ai/patterns/fan-out))
6. **Never on a click.** Opening Program, editing, dragging, linking, recalculating, generating, regenerating, fitting, exporting and printing make zero Jev calls. All three Jev uses run as background jobs in the existing worker with `jev.PriorityBackground`.
7. **Code fast paths first.** An exact or normalised label match, or a parsed R7 table row, is settled by rule with `decided_by = rule` and leaves the Jev call. Jev only for real ambiguity. ([Intent routing](https://docs.typesafe.ai/patterns/intent-routing))
8. **Question authoring (SCHEMA rules 1–9).** Atomic; literal, naming the state field in backticks; positive phrasing; criteria agree with instructions; no thresholds in questions; narrow `runs_on`; ask what a document can show ("does this passage state…").
9. **Choice limits.** At most `jev.MaxChoiceOptions` (255) options, always including `none`. If candidates exceed the cap, code shortlists first (full-text or fuzzy match). Never drop `none`.
10. **Per-question thresholds from calibration.** Thresholds live in `data/program/thresholds.json`, keyed by question family and option count, written by an eval command. A missing threshold authorises nothing: the answer stays blank. Choice confidence depends on option count, so thresholds never transfer between questions. ([Confidence](https://docs.typesafe.ai/confidence), [Confidence routing](https://docs.typesafe.ai/patterns/confidence-routing))
11. **Version the questions.** Each question map has a `QuestionVersion` constant (pattern: `internal/proposals/thresholds.go`). Any wording or option-shape change is a new version and needs a new calibration run.
12. **Only relevant state.** Send the excerpt or rows the question needs, size-checked with `jev.CheckRequestSize` and shrunk in steps like `proposals.Draft.Call()`. (jev-1.13 §5)
13. **Failure is visible, never blocking.** Timeout or error leaves the answer grey with background retry; a grey or blank answer never changes the program.
14. **A reading is a proposal.** Jev results are written as proposals the user accepts. They never overwrite a user value or an accepted value.
15. **Test with recorded responses.** Replay recorded Jev responses in unit tests; the live run is nightly only. Pin an exact model version, never `jev-latest`. ([API](https://docs.typesafe.ai/api))

### Product rules

1. **Unknown stays unknown.** A duration comes only from the user, an accepted document reading, a Profile planning value, or a library row with `status: reviewed`. Draft library rows are never used at runtime. No default durations in code.
2. **User values are never overwritten.** Nothing outside the Program changes a program row without the user adopting it in the review (section 7.4).
3. **Nothing downstream changes silently.** A stage change offers Update or Keep on each RFP, contract and fee schedule; frozen baselines and issued history never change (section 7.6).
4. **Two tiers only.** A stage has no parent; every other row's parent is a stage. Refuse anything that would create a third tier.
5. **Never default the favourable case.** Ground conditions, structural adequacy and compliance are never assumed favourable (`knowledge/profile/planning_keys.yaml` header).
6. **Statutory periods stay `verified: false`** until checked against the instrument itself.
7. **Every row carries `org_id`.** Extend the access sweep test (`internal/httpapi/access_sweep_test.go`) to every new route.
8. **Budgets gate the build.** New paths go in `bench/budgets.json` (section 11).
9. **Dates are `YYYY-MM-DD` strings** in the database, API and UI. Never a JavaScript `Date` for program logic; no time zones.
10. **Derived values are computed, not stored.** Store inputs (durations, links, constraints, calendar). Compute dates, float and critical path on read.
11. **No new runtime dependency.** React, TypeScript, Vite and Go only. Vitest is the one dev dependency.
12. **Do not widen the feature.** If you see a follow-up, name it in the PR and leave it.

## 3. Architecture

Go owns generation, scheduling maths and storage; the browser mirrors the engine only to preview drags; Jev sits off to the sid ine in background jobs that produce proposals.

**Flow on a normal open:** browser `GET /program` → store loads inputs → Go engine computes dates → JSON to the browser → chart renders. No Jev.

**Flow on an edit:** pointer drag → TypeScript engine previews every frame → on release, one `POST /program/ops` → Go validates, applies, recomputes inside one transaction → returns the authoritative state → SSE `program.changed` to other viewers.

**Flow on a Jev reading:** a file dropped on Program, a proposal with an R7 Program table, or a new certificate passage → worker job → code harvests candidates → rules settle what they can → one background fan-out for the rest → proposals written → SSE → user accepts.

## 4. Knowledge library

Four new YAML files under `knowledge/program/` hold everything generation needs; the program never contains a number that is not in one of them, in the Profile, in a document or typed by the user.

All four follow `knowledge/SCHEMA.md` common fields (`version: 1`, `status`, `sources`, optional `notes`), use the existing `applies_when` predicate operators, and are written `status: draft`. Only the owner marks rows `reviewed`. Add a section "Program library (2026-10-18)" to `SCHEMA.md` describing each file exactly as below, and extend `tools/check_knowledge.py` so it passes.

**Placeholder warning for implementers.** Angle-bracket values below (`<n>`) are placeholders showing shape. Never commit them as data, and never fill them from memory, seeds or the web. Content is authored separately in WP-P13.

### 4.1 `skeletons.yaml` — stage patterns

A skeleton picks which stages exist and how they link, by work type, approval pathway and procurement route. Stage ids must exist in `knowledge/works/stages.yaml`.

```yaml
version: 1
status: draft
skeletons:
  - id: sk.new-traditional-da
    label: New building, traditional procurement, development consent
    applies_when:
      all:
        - {det: work_type, eq: new}
        - {det: procurement_route, eq: traditional}
        - {det: approval_pathway, eq: da}
    stages: [investigation, concept_design, approval_documentation, approvals,
             construction_documentation, procurement, construction, completion, defects]
    links:
      - {from: approval_documentation, to: approvals, type: FS, lag: null}
      - {from: approvals, to: construction, type: FS, lag: null}
    status: draft
    sources: [...]
```

- `id` matches `^sk\.[a-z0-9-]+$`.
- `stages` lists catalogue stage ids in order as one flat tier: these become the program's stages, and catalogue sub-stages appear here as ordinary stages. v1 applies one skeleton per project; there is no toggle between skeletons. `links` reference ids in `stages`. `type` is one of `FS`, `SS`, `FF`, `SF`. `lag` is `null` or a duration id (`du.*`), never a literal number.
- Exactly one fallback skeleton `sk.generic` with no `applies_when`: every catalogue stage in order, with a top-level stage replaced by its sub-stages where it has more than one (amended 19 October: Construction's single sub-stage is a fee item, so Construction stays), from `stages.yaml`, chained FS, no lags.
- If more than one skeleton matches, the checker cannot know; generation picks the one with the most predicate terms and records the tie as a check message. The checker must reject two skeletons with identical predicates.

### 4.2 `fragments.yaml` — activities a system brings

```yaml
version: 1
status: draft
fragments:
  - id: fr.basement-excavation
    label: Basement excavation and retention
    stage: construction
    systems: [substructure.basement]
    applies_when: {system_present: substructure.basement}
    activities:
      - {key: shoring, label: Install shoring, systems: [substructure.basement], duration: du.shoring-per-m}
      - {key: bulk-ex, label: Bulk excavation, systems: [site.earthworks], duration: du.bulk-excavation}
    links:
      - {from: shoring, to: bulk-ex, type: SS, lag: du.shoring-lead}
    attach: {after: stage_start, before: fr.substructure-slab}
    status: draft
    sources: [...]
```

- `id` matches `^fr\.[a-z0-9-]+$`; activity `key` is unique within the fragment.
- `systems` on each activity are system ids from `systems.yaml` and cluster files. Hold points (4.5) attach by these ids.
- `attach.after` and `attach.before` are `stage_start`, `stage_finish` or another fragment id. These become FS links with no lag.
- `duration` is a `du.*` id or `null` (unknown).
- `fragments.yaml` must not duplicate an activity a skeleton already provides.

**Revision 2: fragments follow work items.** Fragments apply to the project's included work items (`work_items` with `inclusion = included`), not merely to systems present. Add a predicate operator `work_action: {system: <id>, any_of: [new, replace, upgrade, alter, repair, remove]}`, evaluated by code over included work items, to `SCHEMA.md` "Predicates" and to the checker. Action `retain` produces no activities. Action `investigate` produces one activity under the Investigation stage. Action `remove` selects demolition fragments. When a fragment yields a single activity, its label is the work item's title, copied as the user wrote it.

### 4.3 `durations.yaml` — the only source of library durations

This mirrors `knowledge/costs/benchmarks.yaml`: with no reviewed applicable row, the duration stays unknown.

```yaml
version: 1
durations:
  - id: du.bulk-excavation
    version: 1
    basis: per_unit            # fixed | per_unit | floor_cycle | time_cost | statutory | lead_time
    driver: {planning_key: excavation_volume, unit: m3}   # omitted for fixed, statutory, lead_time
    unit_days: working           # working | calendar
    low: "<n>"                   # decimal strings, never floats
    typical: "<n>"
    high: "<n>"
    applies_when: {...}
    geography: <text>
    limitations: [<text>]
    status: draft
    sources: [...]
```

| `basis` | Inputs | Code computes | Notes |
| --- | --- | --- | --- |
| `fixed` | none | `low`, `typical`, `high` as given | For stages that do not scale. |
| `per_unit` | driver value | `ceil(driver × rate)` for each of low, typical, high | Rate is days per unit. Driver unknown → unknown. |
| `floor_cycle` | `rise_in_storeys` (or a part's storeys) | `ceil(storeys × cycle)` | Cycle is days per floor. |
| `time_cost` | construction budget from Cost Plan, `price_date` | `ceil(K × C^B)` | Bromilow time–cost model. Extra fields `k`, `b`, `cost_base_date`, `index_basis`; cost indexed to the source's base date before use. Budget unknown or a range → use range ends. |
| `statutory` | none | as given | Extra fields `instrument`, `clause`, `verified: false` until checked against the instrument. |
| `lead_time` | none | as given | Long-lead items (lifts, switchboards, façade). |

- `id` matches `^du\.[a-z0-9-]+$`; `low ≤ typical ≤ high`; all non-negative decimal strings with at most 2 decimal places.
- Rounding: always round **up** to whole days, in Go, after computing each bound. Use `math/big` for `per_unit` and `floor_cycle`; `float64` is acceptable only for `time_cost` exponentiation, rounded up at the end. Write a comment explaining why.
- Runtime uses a row only when `status: reviewed`. Draft rows are loaded and validated but never applied.

### 4.4 `calendars.yaml` — non-working days

```yaml
version: 1
calendars:
  - id: cal.nsw-2027
    state: NSW
    year: 2027
    working_week: [mon, tue, wed, thu, fri]
    days:
      - {date: "2027-01-01", kind: public_holiday, label: New Year's Day}
      - {date: "<yyyy-mm-dd>", kind: rdo, label: Industry RDO}
      - {from: "<yyyy-mm-dd>", to: "<yyyy-mm-dd>", kind: shutdown, label: Christmas shutdown}
    verified: false
    status: draft
    sources: [...]
```

- `kind` is `public_holiday`, `rdo` or `shutdown`. Dates are quoted strings.
- Each calendar covers one state and one year. A program spanning a year with no calendar row shows the check "No holiday data for 2029; weekends only".
- The project calendar (section 5) starts as a copy of the matching rows; the user can add, remove or edit days. Edits never write back to the library.
- YAML trap: quote `kind` values and never use bare `on`, `off`, `yes`, `no`.

### 4.5 Hold points — no new file

Hold points come from existing `type: sequences` interfaces that carry `hold_point: {before, after, evidence}` in `knowledge/clusters/*/interfaces.yaml`. Generation inserts one when both the `before` and `after` systems are present and at least one program activity is tagged with each (section 7). Do not copy them into `knowledge/program/`.

Add to `knowledge/profile/planning_keys.yaml`, `status: draft`, owner review required:

- `approval_pathway` — choice: `exempt`, `cdc`, `da`, `ssd`, `other`.
- `procurement_route` — choice: `traditional`, `design_and_construct`, `construction_management`, `other`.
- `excavation_volume` — number, `m3`, scope `site` (only if a reviewed `per_unit` row needs it).

Existing keys reused: `gross_floor_area`, `construction_duration` (weeks), `target_completion`. Existing facts reused: `consent_date`, `consent_lapse_date`, `defects_liability_period`, `contract_form`, `contract_basis`. Check with the owner whether `work_type` from `knowledge/profile/taxonomy.yaml` is already a determinant; if not, add it the same way (open question Q1).

Also add one catalogue entry to `knowledge/works/stages.yaml`: `{id: other, label: Other stage}`, `status: draft`, owner review (Q5). A stage the user creates in Program maps to `other` until the user picks a catalogue stage for it, so the existing `package_stages` validation (`internal/procurement/packages.go`, which requires a catalogue stage id) keeps passing.

### 4.7 Checker rules to add

1. Every id unique and in the right form; every reference resolves (stage, system, fragment, duration, planning key, determinant).
2. Predicates use only the documented operators.
3. Decimal strings parse, are non-negative and satisfy `low ≤ typical ≤ high`.
4. `statutory` rows carry `instrument`, `clause` and `verified`.
5. Fragment links form no cycle; skeleton links form no cycle.
6. Calendar dates parse, fall in the stated year, and `from ≤ to`.
7. Exactly one `sk.generic`.

## 5. Data model and migration

One migration, `internal/db/migrations/035_program.sql`, adds seven tables that store only inputs and links `package_stages` to the program's stages; dates, float and the critical path are computed on every read.

Follow the conventions in `017_packages.sql`: composite primary key `(org_id, id)`, `org_id` first with `ON DELETE CASCADE` to `orgs`, a composite foreign key `(org_id, project_id)` to `projects`, `version bigint` for optimistic concurrency, `retired_at` instead of hard deletes for anything a user may want back, and `CHECK` constraints for every closed set. Add a migration test `internal/db/migrate_program_test.go` like `migrate_packages_test.go`, and extend `migration_rehearsal_test.go`.

```sql
CREATE TABLE programs (
 org_id uuid NOT NULL REFERENCES orgs(id) ON DELETE CASCADE,
 id uuid NOT NULL,
 project_id uuid NOT NULL,
 start_date date,                         -- null: relative weeks
 start_origin text CHECK (start_origin IN ('user','document','profile')),
 skeleton_id text,                        -- sk.* used at generation
 library_version text NOT NULL,           -- hash of knowledge/program at generation
 stage_revision bigint NOT NULL DEFAULT 1 CHECK (stage_revision>0),  -- bumps on any stage add, rename, delete or reorder
 working_week smallint NOT NULL DEFAULT 31 CHECK (working_week BETWEEN 1 AND 127), -- bitmask Mon=1 … Sun=64
 version bigint NOT NULL DEFAULT 1 CHECK (version>0),
 created_by_surface text NOT NULL CHECK (created_by_surface IN ('program','procurement','cost_plan')),
 created_at timestamptz NOT NULL DEFAULT now(),
 updated_at timestamptz NOT NULL DEFAULT now(),
 PRIMARY KEY (org_id,id),
 UNIQUE (org_id,project_id),              -- one program per project
 FOREIGN KEY (org_id,project_id) REFERENCES projects(org_id,id) ON DELETE CASCADE
);

CREATE TABLE program_activities (
 org_id uuid NOT NULL REFERENCES orgs(id) ON DELETE CASCADE,
 id uuid NOT NULL,
 program_id uuid NOT NULL,
 parent_id uuid,                          -- null exactly for stages
 ordinal integer NOT NULL CHECK (ordinal>=0),
 kind text NOT NULL CHECK (kind IN ('stage','activity','milestone','hold_point')),
 label text NOT NULL CHECK (length(trim(label)) BETWEEN 1 AND 200),
 catalogue_stage_id text,                 -- stages only: catalogue id, 'other' for user-made stages
 package_id uuid, package_stage_id uuid, work_item_id uuid,
 fragment_id text, interface_id text,
 systems text[] NOT NULL DEFAULT '{}',
 duration_days integer CHECK (duration_days BETWEEN 0 AND 3650),   -- null: unknown
 duration_low integer, duration_high integer,
 duration_origin text CHECK (duration_origin IN ('user','document','profile','library','calculation')),
 duration_source jsonb NOT NULL DEFAULT '{}' CHECK (jsonb_typeof(duration_source)='object'),
 constraint_kind text NOT NULL DEFAULT 'asap' CHECK (constraint_kind IN ('asap','snet','mso')),
 constraint_date date,
 review_status text NOT NULL CHECK (review_status IN ('proposed','accepted')),
 origin text NOT NULL CHECK (origin IN ('library','user','document')),
 source_key text,                         -- deterministic key for regeneration and review
 dismissed_reason text,                   -- hold points only
 retired_at timestamptz,
 version bigint NOT NULL DEFAULT 1 CHECK (version>0),
 PRIMARY KEY (org_id,id),
 FOREIGN KEY (org_id,program_id) REFERENCES programs(org_id,id) ON DELETE CASCADE,
 FOREIGN KEY (org_id,parent_id) REFERENCES program_activities(org_id,id),
 CHECK ((kind='stage') = (parent_id IS NULL)),           -- two tiers
 CHECK (kind='stage' OR catalogue_stage_id IS NULL),
 CHECK (kind<>'stage' OR catalogue_stage_id IS NOT NULL),
 CHECK ((duration_low IS NULL) = (duration_high IS NULL)),
 CHECK (duration_low IS NULL OR (duration_low <= duration_high)),
 CHECK ((constraint_kind='asap') = (constraint_date IS NULL)),
 CHECK (kind<>'milestone' OR duration_days=0),
 CHECK (kind='hold_point' OR dismissed_reason IS NULL)
);
CREATE UNIQUE INDEX program_activities_source_uq ON program_activities(org_id,program_id,source_key)
 WHERE source_key IS NOT NULL AND retired_at IS NULL;

CREATE TABLE program_links (
 org_id uuid NOT NULL REFERENCES orgs(id) ON DELETE CASCADE,
 id uuid NOT NULL,
 program_id uuid NOT NULL,
 pred_id uuid NOT NULL,                   -- a stage or an activity
 succ_id uuid NOT NULL,
 type text NOT NULL CHECK (type IN ('FS','SS','FF','SF')),
 lag_days integer NOT NULL DEFAULT 0 CHECK (lag_days BETWEEN -365 AND 365),
 lag_unit text NOT NULL DEFAULT 'working' CHECK (lag_unit IN ('working','calendar')),
 origin text NOT NULL CHECK (origin IN ('chain','library','user','document','interface')),
 interface_id text,
 source_key text,
 retired_at timestamptz,
 version bigint NOT NULL DEFAULT 1 CHECK (version>0),
 PRIMARY KEY (org_id,id),
 FOREIGN KEY (org_id,program_id) REFERENCES programs(org_id,id) ON DELETE CASCADE,
 FOREIGN KEY (org_id,pred_id) REFERENCES program_activities(org_id,id),
 FOREIGN KEY (org_id,succ_id) REFERENCES program_activities(org_id,id),
 CHECK (pred_id<>succ_id),
 CHECK (origin<>'chain' OR (type='FS' AND lag_days=0))
);
CREATE UNIQUE INDEX program_links_pair_uq ON program_links(org_id,pred_id,succ_id) WHERE retired_at IS NULL;

CREATE TABLE program_calendar_days (
 org_id uuid NOT NULL REFERENCES orgs(id) ON DELETE CASCADE,
 program_id uuid NOT NULL,
```

**Rules the store enforces (not the schema).**

- **Two tiers.** A non-stage row's `parent_id` must be a live stage of the same program. A stage can never become a child while it has children of its own.
- **Links** join two live rows of the same program, never a row and its own parent, and never form a cycle. Check with the engine before commit and refuse with the cycle path. Links to and from stages are allowed (section 6.5).
- **Chain links** (`origin = chain`) are the default sequence: FS, no lag, between neighbouring stages, and between neighbouring activities inside a stage that have no other predecessor. Reordering rewrites only chain links (section 9.4). User, library, document and interface links never change on a reorder.
- **Stage revision.** Any add, rename, delete or reorder of a stage bumps `programs.stage_revision` in the same transaction.
- **Limits.** At most 5,000 live rows and 20,000 live links per program; refuse beyond that with a plain message.
- **Version pins.** Every write takes the program `version` from the request, bumps it once per batch, and returns 409 on mismatch, like the Cost Plan `pin()` pattern in `web/src/costApi.ts`.
- **Source keys** are deterministic: `skeleton:<sk>:<catalogue stage>`, `package:<package id>:<package stage id>`, `fragment:<fr>:<work item id>:<key>`, `hold:<if.id>`. The review and regeneration match by `source_key`, never by label.
- **Retired rows** keep their links retired with them; undo restores both.

## 6. Scheduling engine

The engine is a pure function, `Compute(Input) Output`, written once in Go (`internal/program/engine.go`, the authority) and once in TypeScript (`web/src/program/engine.ts`, drag preview only), and both must pass the same JSON fixtures.

### 6.1 Time model

- Time is an integer **working-day index**. Index 0 is the first working day on or after the program start date. With no start date, index 0 is "Week 1, day 1" and the calendar treats every Monday–Friday as working (no holidays).
- Intervals are **half-open**: an activity occupies `[start, finish)`. `finish = start + duration`. A 5-day activity starting at 0 has `finish = 5`; its last working day is index 4.
- **Display:** start date = `date(start)`; finish date = `date(finish − 1)` when duration > 0; a milestone shows `date(start)` only. Write this conversion in one helper in each language and use it everywhere. Off-by-one errors here are the most likely bug.
- `calendar.go` / `calendar.ts` provide `dateOf(index) string`, `indexOnOrAfter(date) int`, `indexOnOrBefore(date) int`, `shiftCalendar(index, days) int`. They read the working-week bitmask and `program_calendar_days`. Precompute a sorted array of non-working dates once per call; each lookup is a binary search.

### 6.2 Link rules

`D` is the successor's duration; `lag` is in working days unless `lag_unit = calendar`.

| Type | Meaning | Forward pass: earliest successor start |
| --- | --- | --- |
| FS | B starts after A finishes | `F_a + lag` |
| SS | B starts after A starts | `S_a + lag` |
| FF | B finishes after A finishes | `F_a + lag − D` |
| SF | B finishes after A starts | `S_a + lag − D` |

- Negative lag (a lead) is allowed. The result is clamped to 0: nothing starts before the program start.
- **Calendar-day lag:** convert the anchor index to a date, add `lag` calendar days, then take `indexOnOrAfter` in the forward pass and `indexOnOrBefore` in the backward pass.

### 6.3 Forward pass

1. Build the graph described in 6.5: every live row is a node, and every stage with children adds a hidden start node and a hidden finish node.
2. Topologically sort with Kahn's algorithm. Break ties by `(outline path of ordinals, id)` so output is deterministic. If nodes remain, return `Output.Cycle` with the labels of one cycle and compute nothing else.
3. For each activity in order: `ES = max(0, all link results, SNET index)`. For `mso`, `ES = mso index`; if any link result is greater, record a conflict check.
4. `EF = ES + D`.
5. Record the **driving links**: every link whose result equals `ES` (ties are all driving).

### 6.4 Backward pass and float

1. Project finish `PF = max(EF)` over known activities.
2. Reverse topological order. Activities with no successors: `LF = PF`.
3. Otherwise `LF = min`(PF, …) over successors of the following (the cap at PF stops an activity finishing after the project): FS → `LS_b − lag`; SS → `LS_b − lag + D_a`; FF → `LF_b − lag`; SF → `LF_b − lag + D_a`.
4. `LS = LF − D`. Total float `TF = LS − ES`. Free float `FF = min over successors of (ES_b − that link's forward result)`, or `PF − EF` when there are none.
5. **Critical** means `TF ≤ 0`. Negative float is shown, never hidden.

### 6.5 Unknowns, ranges and summaries

- **Unknown durations.** An activity with `duration_days = null` is unknown. Every row reachable from it through links is also unknown. Unknown rows have no dates and are excluded from the critical path. `Output.Status` reports counts, for example "Indicative: 31 of 44 durations known".
- **Ranges.** Run the passes three times using low, typical and high durations. User, document and profile durations have the same value in all three runs. The completion range is `[PF_low, PF_high]`; bars draw the typical run.
- **A stage with no children** is scheduled exactly like an activity: its own duration and its own links. This is what makes a quick stages-only program work.
- **A stage with children** has no duration of its own; its bar spans the earliest start to the latest finish of its children. It gets two hidden zero-duration nodes, `Start(S)` and `Finish(S)`. Every child must start no earlier than `Start(S)`, and `Finish(S)` must come no earlier than every child's finish. Hidden nodes are never displayed or returned as rows.
- **Links on a stage with children.** Into the stage: only FS and SS, anchored on `Start(S)`. Out of the stage: FS and FF anchor on `Finish(S)`; SS and SF anchor on `Start(S)`. Refuse FF and SF into a stage with children with the message "Link to an activity inside the stage instead".
- **First child.** When the first activity is added to a stage that had its own duration, the activity takes that duration and the stage keeps its links (now on its hidden nodes). Toast: "Design's 40 days moved to Concept design. Undo."
- **Last child removed.** The stage becomes a leaf again with a duration equal to its last span in working days, and a toast says so.
- **Views do not affect computation.** Collapsed and expanded are display only.

### 6.6 Checks

`checks.go` returns a list of `{code, activity_id?, message}` computed in Go only. Initial set:

| Code | When | Message |
| --- | --- | --- |
| `consent_lapse` | Construction stage start date is after `consent_lapse_date` | Construction starts after consent lapses on 12 March 2028. |
| `target_completion` | `target_completion` is earlier than the computed finish | Finish is 6 weeks after the target completion of 30 June 2028. |
| `mso_conflict` | A mandatory start is earlier than its links allow | Framing must start 3 May but Slab holds it until 17 May. |
| `calendar_gap` | The program spans a year with no calendar rows | No holiday data for 2029; weekends only. |
| `hold_point_unlinked` | A hold point lost its before or after link | Hold point has no successor. |
| `skeleton_tie` | Two skeletons matched equally | Two program templates fit; using the one with more conditions. |
| `package_removed` | A package with edited rows was removed in Procurement | Package removed in Procurement. |

Dates in messages use the existing app date format. Messages never claim a breach of law; they state the dates.

Format of each file in `internal/program/testdata/engine/*.json`:

```json
  "name": "ff-negative-lag",
  "calendar": {"start": "2027-03-01", "working_week": 31, "days": [{"day": "2027-03-08", "kind": "public_holiday"}]},
  "activities": [{"id": "a", "duration": 5}, {"id": "b", "duration": 3}],
  "links": [{"pred": "a", "succ": "b", "type": "FF", "lag": -1, "lag_unit": "working"}],
  "expect": {"finish": 5, "activities": {"a": {"es": 0, "ef": 5, "ls": 0, "lf": 5, "tf": 0, "ff": 0, "critical": true}, "b": {"es": 1, "ef": 4, "ls": 2, "lf": 5, "tf": 1, "ff": 1, "critical": false}}}
```

**Performance targets:** Go `Compute` on 2,000 activities and 4,000 links under 2 ms; TypeScript under 5 ms on a mid-range laptop. Algorithm is O(V + E); no recursion (deep chains would overflow the stack).

## 7. Generation, the stage plan and the review

Generation is deterministic Go code with no Jev call; it runs once to create the program, after which nothing outside the Program changes it without the user adopting the change.

### 7.1 Inputs (all read by code, no Jev)

| Input | From |
| --- | --- |
| Work type, NCC class, rise in storeys, state, heritage, other determinants | Profile, existing determinant values |
| `approval_pathway`, `procurement_route`, `gross_floor_area`, `construction_duration`, `target_completion` | Profile planning values (section 4.6) |
| `consent_date`, `consent_lapse_date`, `defects_liability_period`, `contract_form` | Profile facts |
| Included work items with their system, part, action and title | `work_items` where `inclusion = included` and not retired |
| Packages and their stages | `packages`, `package_stages` (live, not cancelled) |
| Construction budget and price date | Cost Plan totals (read-only) |
| Hold points | `sequences` interfaces with `hold_point` |
| Library | `knowledge/program/*.yaml`, reviewed rows only for durations |

### 7.2 Creating the program (`internal/program/generate.go`)

`prepare` runs when the user opens Program, or when Procurement or the Cost Plan first needs stages and no program exists (section 7.6). It is idempotent.

1. **Skeleton.** Evaluate every skeleton's `applies_when`; pick the match with the most predicate terms, else `sk.generic`. A predicate over an unknown determinant is false, never true. Record the choice and why ("AS 4902 contract: design and construct") for the completion header.
2. **Stages (tier 1).** One `stage` row per skeleton stage, `catalogue_stage_id` set, `source_key = skeleton:<sk>:<stage>`. Add chain links between neighbouring stages plus the skeleton's own links.
3. **Package activities (tier 2).** For each live package and each of its package stages, one activity under the program stage with the same `catalogue_stage_id`, labelled "\<package title>: \<stage label>", `package_id` and `package_stage_id` set. A package with no stages (a works or supply package) gets one activity under Construction or Procurement, labelled with the package title. Write `program_stage_id` back onto each `package_stages` row.
4. **Fragment activities (tier 2).** For each fragment whose `applies_when` is true over included work items (section 4.2), add its activities under its stage, its internal links and its `attach` links. A single-activity fragment takes the work item's title as its label.
5. **Conditional fragments.** If a fragment's predicate is unknown, add it with `duration_low = 0` and its normal high bound, so it lengthens only the high run. Label it "If basement" using the determinant's label.
6. **Hold points (tier 2 milestones).** For each `sequences` interface with `hold_point`, if activities exist tagged with both the `after` and `before` systems, insert a `hold_point` milestone in the stage of the last `after` activity, linked FS with no lag on both sides, `source_key = hold:<if.id>`, label `Hold point: <evidence text>` copied from YAML.
7. **Chain links inside stages.** Activities in a stage that have no predecessor from steps 3–6 are chained FS in ordinal order (`origin = chain`).
8. **Durations,** first match wins: user value; accepted document reading; Profile planning value (`construction_duration` applies to the Construction stage only while it has no child with a duration); reviewed library row with true predicates and a known driver (section 4.3); otherwise unknown.
9. **Start date** stays null. Offer `consent_date` as a one-tap suggestion in the question strip; never apply it automatically.
10. **Write** everything `review_status = proposed`, `origin = library`, in one transaction, and return the computed output.

### 7.3 The one question (question strip)

The strip shows the single unknown fact that would narrow the completion range most. Code chooses it:

1. Collect unknown determinants and planning values that any skeleton, fragment or duration predicate or driver references.
2. For each, for each possible value (booleans: true and false; choices: each option; numbers are asked as "Enter gross floor area" only if a reviewed row needs them), regenerate in memory and compute `PF_high − PF_low`.
3. Score = current width minus the worst-case width after answering. Ask the highest score. Ties break by determinant order in `determinants.yaml`.
4. Cap work at 32 in-memory regenerations per request, scoring the first 32 by determinant order. Record the cap in a code comment.

Answering writes the **Profile** value through the existing Profile edit path. Because the user answered inside Program, the resulting program changes apply at once as one undoable batch, with a toast; they do not go to the review. "Not sure" dismisses the question until the Profile value changes.

### 7.4 Ask-first review (replaces automatic regeneration)

After the program exists, a change made elsewhere never edits it directly.

1. A background job `program_review` runs when Profile values, work items, packages, package stages or the library version change on a project with a program (subscribe to the existing events; debounce 2 seconds per project).
2. It regenerates in memory, diffs against the live program by `source_key`, and writes one `program_changes` row per difference: `add`, `remove`, `rename`, `duration` or `link`, each with a plain summary and the exact op that Adopt would apply. It writes nothing to the program itself. An older pending row for the same `source_key` becomes `superseded`.
3. The Program shows a banner: "Scope and procurement changed: 3 to add, 1 to remove, 2 renamed. Review." The review lists each change with Adopt and Keep, plus Adopt all.
4. **Default choice:** Adopt for rows still proposed and unedited; Keep for anything the user created, edited or accepted. Example: "Basement removed from scope; you edited Basement excavation" defaults to Keep.
5. Adopting applies the selected ops as one batch through the normal ops path (section 8.1), so it is undoable and version-pinned. Keep marks the change `kept`; the same difference is not raised again until its inputs change again.
6. Accepted document readings (section 10) follow the same principle: a reading is a proposal until the user accepts it.

No Jev call is involved anywhere in the review.

### 7.5 Two views: collapsed and expanded

| View | Shows | Editing |
| --- | --- | --- |
| Collapsed | Stage rows only. A stage with activities draws one bar spanning them; a stage without activities draws its own bar. | Rename stages, reorder stages, link stages, resize a stage that has no activities, drag a stage with activities to shift all of them together. |
| Expanded | Stages with their activities beneath. | Everything. |

- Each stage has its own chevron; the toolbar has **Collapse all** and **Expand all**. There is no other level of detail.
- Expand state is a per-user view preference kept in the browser (`localStorage` keyed by project id, wrapped in try/catch, defaulting to collapsed). It is not stored on the program and has no undo entry.
- Links between activities in two collapsed stages draw as one faint line between the stage bars.

### 7.6 One stage plan shared with Procurement and the Cost Plan

The program's stages are the project's stage plan. Program is where stages are edited; Procurement and the Cost Plan point to them.

**Whichever surface comes first creates it.** Creating an RFP, adding a package stage, or adding a fee line by stage when no program exists calls `prepare` (section 7.2) with `created_by_surface` set. When the user later opens Program, the same stages are there.

**Procurement.**

- `procurement.DefaultStages` reads the program's stages instead of copying the catalogue: services packages get the program stages whose `catalogue_stage_id` is one of the catalogue sub-stages they get today, in program order, with `program_stage_id` set.
- Each package row gets a small stage picker (`web/src/PackageStages.tsx`): a checkbox per program stage. Ticking one creates a `package_stages` row through the existing endpoint; unticking retires it. Labels come from the program stage. Procurement cannot add or rename stages.
- RFP stage rows (R7 Program, fee schedule) are built from the package stages, as now.
- Award writes cost lines per package stage, as now. Contract values still come only from the firm's priced cells.

**Stage revision and Update or Keep.** Each package stage set and each RFP draft records the `stage_revision` it was built from. When the program's revision is newer, that document shows the differences (by stable stage id, so a rename is never mistaken for a delete and add) and offers Update or Keep:

| Document | Update means |
| --- | --- |
| Package stages | Renames copy across; added program stages are offered as unticked boxes; a removed program stage retires its package stage unless money is attached (next rows). |
| Draft RFP | Rewrites its stage rows. |
| Issued RFP | Creates a new draft revision. The issued version stays as history. |
| Proposals received | Never changed. Stages are matched by id; any mismatch is flagged. |
| Awarded contract and its cost lines | Renames may flow through. Added stages become new unpriced lines. Contract values stay as the firm priced them. |
| A stage with invoices or awarded money | Cannot be removed downstream. It is marked "removed from program" and kept. |
| Frozen cost baseline | Never changed. |

Keep records the revision as acknowledged so the offer does not repeat until the stages change again. Flow is one way, Program to downstream. All of this is code; no Jev.

### 7.7 Evidence and stages

Document evidence fills the stages; it never chooses or changes them.

- **Precedence for any value:** user, then accepted document evidence, then Profile facts and planning values, then the reviewed library, then unknown.
- Evidence about a stage (for example the architect's R7 weeks for Approval documentation) is stored with the `catalogue_stage_id` it was matched to. It applies to the program stage with that id, so renaming or reordering stages never loses it.
- If the user deletes the stage that evidence belongs to, the evidence stays and a notice says "Evidence for Approval documentation has no stage. Add the stage back or dismiss."
- A user-made stage (`other`) receives evidence only when the user assigns it.
- Profile facts may inform the skeleton choice (for example an AS 4902 contract selects a design-and-construct skeleton). Regime switching between alternative skeletons is out of scope for v1.

| `link_update` | `id`, any of `type`, `lag_days`, `lag_unit` |  |
| `link_delete` | `ids[]` |  |
| `set_start` | `start_date` or null |  |

**Validation at the boundary** (return 422 with a plain message naming the field): label 1–200 characters after trimming; durations 0–3,650; lag −365 to 365; dates match `^\d{4}-\d{2}-\d{2}$` and parse; every id belongs to this program and org; at most 500 ops per batch; at most 5,000 live activities.

**Concurrency.** Stale `version` → 409 with the current state in the body. The client replaces its state, re-applies nothing automatically, and shows "Someone else changed the program; showing their version."

**Undo.** `program_ops` stores each batch with a server-computed inverse. Undo applies the inverse of the caller's most recent non-undone batch, if the rows it touches still have the versions that batch produced; otherwise refuse with "Can't undo: changed since". Redo re-applies. Undo history is per user.

## 9. Frontend: the Program view

The chart is hand-built React and SVG in four layers, with drags handled outside React state so they run every frame; there is no Gantt library and no new runtime dependency.

### 9.1 Screen layout

Top to bottom:

1. **Toolbar:** Collapse all / Expand all, Fit to screen, Fit to selection, Fit height, Links on/off, zoom out/in, Today, Undo, Redo, Link in sequence (enabled when two or more rows are selected), Accept all (only when proposals exist, with a count), Review changes (only when the review has items, with a count), Import, Export, Print.
2. **Question strip:** one question with tap answers, plus the one-tap start date suggestion. Hidden when there is nothing to ask. Never blocks the chart.
3. **Completion header:** finish date (typical) and range, status words ("Indicative: 31 of 44 durations known"), the skeleton and why it was chosen, and a checks count that expands to the list.
4. **Split pane:** grid on the left, chart on the right, a draggable divider, one shared vertical scroll. Stage rows are bold with a chevron; activity rows are indented one level. On a screen narrower than 720 px the grid shows only the name column.

Enable the existing nav entry: remove `idle: true` from the `program` entry in `web/src/LeftNav.tsx` and route it to `Program.tsx`. Empty state when no program exists: one ember button "Build program" that calls `prepare`.

### 9.2 Rendering

- **Layers,** each its own component and SVG group, in this order: `Timescale` (header, weekend and non-working shading, today line), `Bars`, `Links`, `Overlay` (drag ghost, snap guide, tooltip, selection box). Memoise the first three on `(state version, zoom, scroll window)`. During a drag only `Overlay` changes.
- **Virtualisation:** fixed row height `rowH` (28 px default, 20–28 px after Fit height). Render rows `floor(scrollTop / rowH) − 10` to `ceil((scrollTop + viewportH) / rowH) + 10`. Links are drawn only if either end is in that window.
- **Geometry** lives in `layout.ts` as pure functions: `x(index) = (index − viewStart) × pxPerDay`, bar width `max(D × pxPerDay, 2)`, milestone diamond 10 px. Unit-test them.
- **Pixel crispness:** gridlines and bar edges at `Math.round(x) + 0.5`; `shape-rendering: crispEdges` on gridlines only.
- **Colours:** only tokens from `web/DESIGN.md` via CSS variables, so light and dark both work. Ember marks user-owned or evidenced values; azure marks library inference; amber marks proposals awaiting review; alert red marks the critical path and conflicts. Every colour meaning also has a second cue (weight, dash, icon or text) because colour alone fails some readers.
- **Bar labels:** inside the bar if it fits (measure once per font with a cached canvas `measureText`), otherwise just after the bar end.
- **Type:** IBM Plex Sans for labels; IBM Plex Mono with `font-variant-numeric: tabular-nums` for dates and durations.

### 9.3 Link lines

`routing.ts` returns an SVG path for each link from the predecessor's anchor (finish x for F, start x for S) to the successor's anchor:

1. Leave the predecessor anchor horizontally by an 8 px stub (right for F, left for S).
2. If the successor anchor is reachable going forward (its x is beyond the stub), go vertically to the successor row's centre, then horizontally into the anchor.
3. Otherwise route around: down to the gap between rows (half a row), across, then down and in.
4. Arrowhead on the successor end, pointing into the anchor (left-pointing for F anchors on FF and SF).

Styles: critical links 2 px in the critical colour; driving links solid; non-driving links dashed; hold-point links carry a small diamond at the midpoint. Lag shows as a label on hover. A transparent 10 px-wide stroke under each path is the click target.

### 9.4 Interactions

| Gesture | Result | Op on release |
| --- | --- | --- |
| Click a name (row already selected), double-click a name, or F2 | Name becomes an input in place; Enter saves, Escape cancels, Tab saves and moves to the next name | `update` with `label` |
| Drag bar body | Ghost bar follows, snapped; successors' ghosts update live; badge "+9 days to completion". With several bars selected, all move together. | `move` |
| Drag a stage bar that has activities | The whole stage and its activities move together | `move` |
| Drag bar left or right end zone | Resize from that end; left end also moves start | `resize` (and `move`) |
| Drag from a start or finish dot onto another bar's start or finish dot | Rubber-band line; target dot highlights | `link_add` with type from the two ends |
| Drop link on a bar's middle |  | `link_add` FS, lag 0 |
| Click a link line | Popover: type, lag, unit, delete | `link_update` or `link_delete` |
| Click empty chart space in a row | Draws a new bar there (drag to size) | `add` |
| Drag selected grid rows (by the row handle) | Insertion line between rows; dropping a stage carries its activities; dropping activities onto a stage row puts them at its end | `reorder` |
| Shift-drag across empty chart space | Selection box adds the bars it touches to the selection | — |

**Selection (`web/src/program/selection.ts`).** One selection shared by the grid and the chart, held as an ordered set of row ids plus an anchor.

- **Click** selects one row and sets the anchor. **Ctrl-click** (Cmd-click on macOS) toggles one row and moves the anchor to it. **Shift-click** selects the range from the anchor to the clicked row in current grid order, replacing the previous range but keeping Ctrl-clicked rows. **Ctrl+Shift-click** adds a range.
- Ranges follow what is visible: in the collapsed view a range covers stages only; selecting a collapsed stage does not select its hidden activities, but moving or deleting it carries them.
- Selected rows and bars share one highlight (ember outline plus a tinted row). The toolbar shows "4 selected".
- **Bulk actions on a selection:** drag (move or reorder), Delete, Shift+Left/Right nudge, indent or outdent, Link in sequence, and set duration (typing a duration with several rows selected applies it to all, after a confirm naming the count).
- Escape or a click on empty space clears the selection.

**Reorder re-sequences.** Default sequence lives in chain links (section 5). When rows are reordered, the server rewrites chain links among the old and new neighbours so the sequence follows the new order, and returns the links it changed. The toast says "Moved Approvals after Construction documentation; sequence updated. Undo." User-drawn links never change on a reorder, and the toast names any that now run backwards ("Framing still waits for Slab").

**Pointer handling** (`chart/useDrag.ts`):

1. Use Pointer Events only (`pointerdown`, `pointermove`, `pointerup`, `pointercancel`). Call `setPointerCapture` on down.
2. Require 4 px of movement before a drag starts, so a click stays a click.
3. On move, store the latest pointer position in a ref and schedule one `requestAnimationFrame`. In that frame: compute the snapped index, run the TypeScript engine on the edited input, write ghost positions with `transform: translateX(...)` directly on the overlay elements. Do not call React `setState` during the drag.
4. On up: build the op batch, update React state optimistically from the TypeScript result, send `POST /program/ops`, then replace state with the server response. If the server refuses, restore the previous state and show its message.
5. On `pointercancel` or Escape: restore and send nothing.

**Hit zones.** End zones are 8 px for `(pointer: fine)` and 24 px for `(pointer: coarse)`, inside the bar if the bar is wide enough, otherwise extending outside it. Link dots appear on hover (fine) or after selecting the bar (coarse). On touch, a long press of 350 ms starts a drag so one-finger scrolling still works. Cursors: `grab`/`grabbing`, `ew-resize`, `crosshair` for linking.

**Snapping.** Snap unit by zoom: day when `pxPerDay ≥ 12`, week otherwise. Show a vertical guide line and the snapped date in the tooltip. Hold Alt to snap to days at any zoom.

**Settle.** After the server confirms, bars ease to their final position over 150 ms with a CSS `transform` transition, disabled under `prefers-reduced-motion: reduce`.

## 10. Jev integration

Jev is used in exactly three background readings, each one fan-out per document or passage, each producing proposals the user accepts; everything else in Program is code.

Copy the structure of `internal/proposals/read.go` for each reading: `NewDraft(evidence, context, userDecisions)` → `rule()` settles what code can → `ask()` builds only the open questions → `Call()` builds one `jev.Call` and shrinks it until `jev.CheckRequestSize` passes → `Apply(result, err, thresholds)` bands each answer → `Finish()` returns readings. Put them in `internal/programread/`.

### 10.1 Where Jev is not used

| Path | Why no Jev |
| --- | --- |
| Generation, regeneration, the one question | Structured facts in, code out. Predicates and arithmetic are code. |
| Durations, dates, float, critical path, ranges, checks | Maths and date comparison are forbidden to Jev (jev-1.13 §2–3). |
| Activity names | Library text or verbatim copies. Jev never writes text (jev-1.13 §9). |
| Open, edit, drag, link, undo, fit, export, print | Navigation and typing never call Jev (`AGENTS.md`). |
| Matching a file row by exact or normalised label | Code fast path (intent routing). |
| Parsing dates, durations and predecessors in a file | Code. Jev never sees a question about a date's value. |

The ask-first review, the shared stage plan, stage sync, every Update or Keep offer, bulk selection and re-sequencing are code only as well. None of them may call Jev.

### 10.2 Reading A: a program file dropped on Program

**Trigger.** The user drops a PDF, DOCX or XLSX on the Program view (or uses Import). It is filed through the normal intake path, unchanged. Filing kinds and the filing fan-out do not change. Then a `program_import` job is queued for that document and program.

**Harvest (code, `harvest.go`).**

1. XLSX: read sheets with `internal/xlsx`. Find the header row by keywords (`task`, `activity`, `name`, `description`; `start`; `finish`, `end`; `duration`; `predecessor`). DOCX: tables. PDF: text lines with at least one date-like token.
2. Produce rows `{id: "r<n>", label, start_raw, finish_raw, duration_raw, predecessors_raw, outline_level?}`, every value copied verbatim.
3. Parse dates in code. Accept `d/m/yyyy`, `d/m/yy`, `d Mon yyyy`, `yyyy-mm-dd`. Decide day-month order per column: if any value has a first part over 12, the column is d/m; if any has a second part over 12, it is m/d; if neither, default d/m (Australian) and add the check "Date order assumed day/month in column Start". A value that does not parse stays raw and unparsed.
4. Parse durations (`5d`, `3 wks`, `10 days`) and predecessors (`12FS+2d`) with the same parser as the grid (`internal/program/parse.go`, mirrored in `grid/parse.ts`).

**Targets.** Live stages first, then package activities, milestones and hold points, then fragment activities while the call stays within the size budget. Evidence matched to a stage is stored with that stage's catalogue\_stage\_id (section 7.7).

**Rules first.** Normalise both labels (lower case, strip punctuation and stage numbers, collapse spaces, apply the existing construction synonym list used by search). An exact normalised match settles the target by rule (`decided_by = rule`). Each file row can settle at most one target.

**Shortlist (code).** For each unsettled target, score unsettled rows by trigram similarity of normalised labels and keep the top 40 with score above zero. A target with an empty shortlist gets no question.

**Question (family `program_row`, one per unsettled target, all in one call).**

```yaml
type: choice
instructions: >-
  Using `rows`, which row of this program is the same work as the activity
  "<target label>" (stage: <stage label>)? Choose none when no row is that
  work.
criteria:
  r12: {row: "<verbatim label of row 12>"}
  r40: {row: "<verbatim label of row 40>"}
  none: No row in this program is the same work as this activity.
```

- The target label and stage label in the instructions come from the program; they are literal text, not generated.
- Criteria show the verbatim row label only. Do not put dates or durations in the criteria or the question: Jev is not asked anything about dates.
- Add boundary guidance to the instructions: "A heading or summary row that only groups other rows is not the same work. A row for a different trade or a different stage of the same trade is not the same work."
- State: `{"filename": "…", "rows": [{"id": "r12", "label": "…", "level": 2}, …]}`, containing only rows that appear in some shortlist. Labels only, no dates (only relevant state, jev-1.13 §5).

**Call.** `jev.PriorityBackground`, `Deadline: 6 * time.Second`, `QuestionVersion: "program-row-1"`. Shrink steps if the request is too large: options per target 40 → 20 → 10; then drop fragment activity targets; then drop package activity targets. Record which targets were not asked; they show "Not matched".

**Apply.** For each answer, look up the threshold for family `program_row` and that option count. Green or amber with a row id (not `none`) → write `program_readings` rows for `start`, `finish` and `duration` with `value` = the raw text and `parsed` = the code-parsed result. Blank → nothing. Error or timeout → band grey, background retry with the existing backoff.

**User sees.** "4 readings from Smith program.xlsx" in the toolbar. Each target shows the proposed dates beside its own; accepting sets the activity's duration (code computes finish − start in working days from the parsed dates) and a `snet` constraint at the parsed start. File rows that matched nothing can be added as new activities by the user in one click (code, no Jev). Predecessor links between matched rows are proposed by code from the parsed predecessor column.

### 10.3 Reading B: the R7 Program returnable in a proposal

SiteWise's own RFP form (`internal/rfp/form.go`, table `r7`) asks each firm for Stage, Your weeks, Authority weeks, and Inputs. Program uses those weeks only after the package is awarded.

**Rules first.** When the proposal is a DOCX or XLSX returnable, find the table whose header matches the `r7` columns exactly. For each row whose Stage cell exactly matches one of our stage labels and whose Your weeks cell parses as a plain number, settle by rule. Most well-completed returnables never reach Jev.

**Harvest for the rest.** From the proposal excerpt, collect duration-like tokens (`6 weeks`, `30 working days`, `4–6 wks`) within 200 characters of each unsettled stage label, verbatim, up to 20 per stage.

**Question (family `program_stage_weeks`, one per unsettled stage).**

```yaml
type: choice
instructions: >-
  Using `excerpt`, which candidate does the proposal state as the firm's own
  duration for the stage "<stage label>"? A duration stated for authority
  review, for a different stage, or for the whole commission is not it.
  Choose none when the proposal states no duration for this stage.
criteria:
  c1: {value: "6 weeks"}
  c2: {value: "30 working days"}
  none: The proposal states no duration of its own for this stage.
```

Code converts the chosen verbatim value to working days. A range (`4–6 wks`) becomes low and high; Jev is never asked to convert or compare.

**Where it runs.** As its own background job `proposal_program`, queued after the existing proposal read finishes, with its own `QuestionVersion: "proposal-program-1"` and its own calibration. Do **not** add these questions to the existing `proposal-1` question map: `internal/proposals/thresholds.go` says any change to that map is a new version needing a new calibration of every proposal question. (Owner decision Q4 can choose otherwise.)

**User sees.** When an award is made, the package's program rows get proposals "From the awarded proposal: Design development 6 weeks". Before award, nothing changes in Program.

### 10.4 Reading C: hold-point release evidence

**Schema change.** In `knowledge/SCHEMA.md` "Interfaces", allow an optional `hold_point.release` question beside `evidence`, authored per interface by the knowledge owner, `status: draft`:

```yaml
hold_point:
  before: substructure.slab-on-ground
  after: structure.concrete
  evidence: Reinforcement inspection release identifying the pour.
  release:
    type: noul
    instructions: >-
      Using `text`, does this passage state that the inspection described in
      `hold_point` was carried out and the work was released to proceed?
    criteria:
      true: >-
        It states the inspection was completed and the work may proceed, or
        it is an inspection release, certificate or approval for that work.
      false: >-
        It only requires, schedules or requests the inspection, or records a
        failed or conditional inspection.
    runs_on: [structure.concrete]
```

**Where it runs.** In the existing background passage pipeline, only on passages labelled with a `runs_on` system and only on documents of kind `certificate`, `report` or `correspondence`, for projects whose program contains that hold point. The question joins that passage's existing single fan-out (one fan-out per state). The state is the standard passage state plus `hold_point` (the evidence text). Before adding it, read how `passage_calls` records question versions and give these questions their own version id so existing passage thresholds stay valid.

**Apply.** Noul answers carry probability only, no confidence ([Confidence](https://docs.typesafe.ai/confidence)). Threshold family `hold_point_release`. Above the green or amber cut-off → a `program_readings` row `field = released`, `status = proposed`, linked to the passage. The hold point shows "Evidence found: \<document title>, page \<n>" with a link.

**Never automatic.** Only a user click marks a hold point released. The release date shown is the document's filed date from code, labelled "document dated". Jev never gives a date.

**Known limit (v1).** One hold point per interface per program, so evidence for one pour cannot be told apart from another. The user judges. Name this in the UI tooltip.

## 13. Edge cases and owner decisions

Implementers handle every edge case below as written; the eight owner questions must be answered in WP-P0 before the packages that depend on them start.

### 13.1 Edge cases

| Case | Required behaviour |
| --- | --- |
| Project has almost no Profile facts | `sk.generic` stages, one activity per package stage, hold points from included work items; all durations unknown; status "Indicative: 0 of 12 durations known"; one question offered. |
| Procurement or Cost Plan used before Program | `prepare` creates the program from that surface; opening Program later shows the same stages, already linked to package stages. |
| No start date | Relative timescale "Week 1…"; weekends only; consent date offered as a one-tap start. |
| Consent lapse date already passed | Show the `consent_lapse` check with both dates; do not block anything. |
| Activity dragged earlier than its links allow | Snap back to the held position; tooltip "Held by Slab"; no write. |
| Bulk move where one selected row is held | Nothing moves; the message names the held rows. |
| Link would create a cycle | Refuse; name the cycle in order, for example "Framing → Roof → Framing". |
| Indent an activity, or indent a stage that has activities | Refuse: "Programs have two levels: stages and activities." |
| Reorder leaves a user-drawn link running backwards | Keep the link; the toast names it. |
| Shift-click range in the collapsed view | Covers stages only; moving or deleting a selected stage carries its hidden activities. |
| Deleting a stage with activities | Confirm stating the number of rows and links removed; one undo restores all. |
| Deleting a stage that has fees, an awarded contract or invoices downstream | Allowed in Program; downstream keeps the stage marked "removed from program" (7.6). |
| Deleting a stage that has evidence | Evidence stays with a notice to add the stage back or dismiss (7.7). |
| Deleting a hold point | Requires a reason; the row is retired, not deleted; a check stays visible. |
| Review item for a row the user edited after it was raised | Default switches to Keep and the item says "You've edited this since". |
| Package removed in Procurement | Appears in the review as a removal; defaults to Keep if its activity was edited. |
| Negative lag beyond the predecessor's start | Allowed; the result clamps at program start (index 0). |
| Milestone resized | Duration above 0 turns it into an activity; confirm once. |
| Year with no calendar data | Weekends only plus the `calendar_gap` check. |
| Two users editing | Version pins; 409 shows the other user's version; no silent merge. |
| Drag in progress when SSE arrives | Refetch after release, not during. |
| Jev down or slow | Readings grey and retried in the background; Program fully usable. |
| Uncalibrated reading | Answers blank; dev status page says not calibrated. |
| Ambiguous day-month dates in a file | Assume day/month and add a check naming the column. |
| Imported file with more than 255 candidate rows for a target | Code shortlist of 40, then shrink steps; never drop `none`. |
| Huge program (over 5,000 rows) | Refuse further adds with a plain message; suggest collapsing stages to work faster. |
| Narrow phone screen | Grid collapses to the name column; the chart scrolls horizontally inside its own container; the page never scrolls sideways. |
| Print of a long program | All rows in the current view across A3 pages, timescale header repeated. |
| Wrong org or missing project | 404, never a hint that it exists. |

### 13.4 As built (21 October 2026)

Where the build differs from the text above, this is what holds.

1. `sk.generic` replaces a top-level stage by its sub-stages only when it has more than one, so Construction stays (4.1, amended).
2. Skeleton predicates read `det: work_type` and a new `cond:` operand over the Profile conditions `planning` and `procurement_route` (Q1). `cond` and `work_action` are valid only in program library files.
3. A program with no start date counts working days from a fixed Monday (2001-01-01) so start constraints work; `set_start` carries constraints across by working-day index.
4. The review runs as a debounced in-process job (2 s per project), kicked after Profile, work item, package and program writes and on opening Program. It never raises a user's own rename, link edit or delete; a removal adopted from the review is raised again when its input returns. Adopt all adopts only changes whose default is Adopt; Keep-default items wait for an explicit choice.
5. Readings A and B run in the server's background readers (the existing proposal-reader pattern) with `jev.PriorityBackground`; Reading C joins the worker's passage fan-out with its own version `hold-point-release-1`. Reading B uses migration 038 on `submissions`; Reading A keeps file state in `program_imports` (migration 037). Stage sync state is migration 036; question dismissals 034; review basis and order 035.
6. No construction synonym list exists in the codebase, so label normalisation uses none. No gold sets exist for `program_row`, `program_stage_weeks` or `hold_point_release`: all three ship uncalibrated and their answers stay blank.
7. The RFP fee table comes from the discipline's stage list, not package stages; stage sync rewrites the program-stage rows recorded on the RFP draft, and the printed RFP is unchanged.
8. The chart's x axis counts working days, so weekends take no width (holidays draw as breaks); fit keeps one day plus 40 px on the left so a start dot is always reachable. Labels use the shell's sans face.
9. Hold points: all authored `hold_point.before/after` values are free text, so generation inserts none until WP-P15 rewrites them as system ids; no `release` question is authored yet.
