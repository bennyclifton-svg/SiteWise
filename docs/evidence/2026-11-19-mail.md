# Mail in and out: what was built and measured

Date: 19 November 2026. Branch `wave/mail`, from local `main` at 6f563f2
(not merged, not deployed). Plans: `docs/plans/2026-11-14-email-intake.md`
(as amended by A1 to A7) and `docs/plans/2026-11-17-correspondence-transmittals.md`.
Lane C (a public unauthenticated webhook, mail in and out, file intake), with
lane A's rules where it files documents. Everything here was run on the
development machine against a private schema of `sitewise_test` (`wave_mail`,
and `wave_mail_e2e` for Playwright).

**Nothing has been run against real Mailgun.** The Mailgun account is
disabled and email intake's Task 0 (the owner's check of a real forwarded
post) has not been run. Every inbound post in the tests is hand-written in
Mailgun's documented `forward()` shape with dummy content and signed with a
test key; every outbound message went to a sink. No live model, Jev or
Mailgun call was made. The feature is off unless `SITEWISE_MAIL_IN_DOMAIN`
and `SITEWISE_MAILGUN_SIGNING_KEY` are both set. The chat key's `mail` group
is draft and not owner-reviewed. No security review has been done.

was not re-measured. The Jev pick joins an email body's existing call: the
call carries one more question, which was not timed against a live Jev.

## 4. Known limits

- **The sender check rests on Mailgun's headers** (Task 0, finding 1). An
  absent header is never a pass, so until it is confirmed a member's mail
  may be held as "Could not confirm the sender". Mailgun reports one DKIM
  result for a message that may carry several signatures. Domain alignment
  is a suffix match without a public-suffix list.
- **A signature covers only timestamp and token.** Every token is recorded
  for two days and a timestamp must be within a day, so a captured post
  cannot be replayed with another body; the body itself is not signed.
- **Mail leaves From `SITEWISE_MAIL_FROM`** as "<Org> via SiteWise" until
  the owner verifies the receiving domain for sending; replies reach the
  project through Reply-To.
- **Sent is not delivered.** A crash after the service accepted a message
  sends it again on the sweep (same Message-ID).
- **A link emailed from Share sits in the message's body**, which every
  team member can read in Messages, as they can make a link themselves.
- **Rate limits are in memory**, as the account and guest limits are.
- The record reads 1,000 messages at most; older ones page with `?before=`
  (not yet offered on the screen).
- Plan 3's two chip buttons (Read as progress claim, Add variation) are
  `readAsProgressClaim` and `addVariation` in `web/src/MailIn.tsx`, returning
  "This isn't available yet."; `CHIP_ACTIONS` keeps their buttons hidden.
- An RFI's status is the PM's: sending it does not move Draft to Open.

## 6. Mailgun assumptions (Task 0 confirms each)

| Assumption | Function | If it is wrong |
|---|---|---|
| `X-Mailgun-Spf` and `X-Mailgun-Dkim-Check-Result` are in `message-headers` | `mailin.Authenticated` | Members' mail is held as unverified; replace this one function |
| `body-plain` is filled for an HTML-only message | `mailin.PlainBody` | The HTML's text is used already |
| The largest post is under 40 MB | `mailin.MaxPostBytes` | Raise or lower the constant |
| `recipient` holds the address received for, also for Bcc; several are comma-separated | `mailin.RecipientLocalPart` | Bcc'd mail is dropped as "not for the mail domain" |
| `In-Reply-To` and `References` are in `message-headers` | `mailin.ThreadHeaders` | Replies start their own threads and outside replies are held |
| The signature is hex HMAC-SHA256 of timestamp then token; a retry reuses it within 8 hours | `mailin.VerifySignature`, `mailin.Fresh` | Every post is refused (406, logged as "signature") |
| Spam filtering on gives `X-Mailgun-Sflag` | `mailin.Dropped` | Spam is held, not dropped |

## 8. Deviations from the plans

- The address is random, not the project's name (the brief's rule).
- One 406 for every refusal, not 401 for a bad signature and 413 for size.
- Every signed token is recorded, not only those of stored messages.
- A `busy` held reason (the hourly cap the brief asks for).
- The plan limit is checked once per message before recording; a filed
  message never becomes held (the trigger forbids it).
- `GET /mail` returns all messages with a `held` count (the plan's 15
  November update).
- Jev's pick is stored with a band and shown only past an approved cut-off,
  as the register's picks are (the brief), rather than "to check" at once.
- Reply-To is stored on the sent row (`reply_to`, migration 076) so the
  outbox never re-derives it.
- From is `SITEWISE_MAIL_FROM` ("<Org> via SiteWise"), decision 2's
  fallback, until the sending domain is verified.
- "Who holds" says "N addresses were sent revision B", never "hold".
- Add to register makes a `notice` row for every pick that is not a claim
  or a variation, the RFI pick included (an RFI the PM raises is a different
  row: one the PM owes, not one owed to the PM).
- Task 8 (links over 10 MB) is not built.
