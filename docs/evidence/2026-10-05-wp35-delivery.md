# WP-35 delivery — implementation in progress

Lane A. Outcome: explicit project dates, risks and approvals for the M1 RFP,
then the remaining delivery/dependency workflows in M2. No inferred progress,
CPM, Gantt or new AI calls. CRUD budget p50 100 ms / p90 250 ms.

Migration 019 defines the final delivery item and finish-to-start dependency
schema. Composite FKs keep work and package references within the project and
stage references within their package. An owner must belong to the same org.
Dependency endpoints and cycle checks are not implemented yet.

The plan leaves per-kind status words unspecified. The implementation uses:

- Activity/action: not_started, in_progress, blocked, complete, cancelled.
- Milestone: planned, achieved, cancelled.
- Risk: open, mitigating, closed.
- Issue: open, in_progress, resolved, closed.
- Decision: open, decided, superseded.
- Approval: not_submitted, submitted, approved, rejected, withdrawn.

Each record validates its own kind/status, exact calendar dates, title bounds,
stage/package pairing and typed details. Risk likelihood/consequence remain
descriptive text; no score or scale is invented. A decided choice must name an
option. Approval submission/determination dates are optional; when both exist,
determination cannot precede submission. These are planning records, not
verification of statutory compliance.

Store create/read/edit and GET/POST/PATCH API routes are implemented. Creates validate live references, resolve
source snapshots against project documents, record the actor, bump delivery
revision and emit the delivery event in one transaction. Open delivery records
block package/stage retirement and work reset; automatic work retirement skips
them. Any delivery reference also blocks undo of the originally created work
or package, including historical use. API writes require membership, matching
origin and project ownership and reject caller-supplied provenance.

Edits require the current version. Omitted dates are preserved; JSON null clears
a date. Kind/status changes append actor/time history inside the transaction;
initial writes record the actor, initial status and time. Approval status never
sets review status to verified. Unchanged source snapshots survive reprocessing.
Closed historical records may reference retired targets, but reopening them or
changing references requires live targets. Dependencies must be removed before
retiring a delivery record. Concurrent edits allow one write and reject the
stale one.

## Approval and hold-point acceptance

Lane A. The user can now accept an approval or hold-point proposal through the
existing proposal endpoint. An approval creates a `not_submitted` approval;
a hold point creates a `planned` milestone under the final delivery schema.
The proposal's original kind, draft state, reasons and fingerprint are retained
in provenance and the decision-time snapshot. Neither acceptance nor an upload
sets a date, owner, approved status, achieved milestone or verified provenance.
Package, work and stage links are explicit optional choices; the implementation
does not guess which package performs the earlier work.

Migration `019a_delivery_proposal_decisions.sql` adds the delivery acceptance
target with a generated conditional foreign key scoped to organisation and
project. Existing migrations are unchanged. Acceptance locks the project,
validates the actor and current fingerprint, resolves any assignment, creates
the delivery item and saves the decision atomically. Successful writes advance
the works/delivery revisions and wake the existing event stream. Retries compare
the original assignment and return the same item even after a projection is
removed. Unsupported kinds fall through to the existing work/package/scope
acceptance paths.

Undo retires only the exact untouched version. Dependencies, another decision
or a saved report using the delivery record block undo. The decision and its
snapshot remain in undo history; reacceptance revives the same identity only
at the version produced by that undo. Human corrections, including changes
of title, are sufficient to refuse undo.

Focused store and HTTP tests pass for both proposal kinds, concurrent retries,
stale versions, missing/invalid assignments, foreign access, draft provenance,
undo/reacceptance, edited records, dependency use and a real saved RFP reference
(`.tools/wp35-accept-tests.log`, `.tools/wp35-accept-api-tests.log`). No new dependency, runtime
AI call or service. The minimum delivery UI and M2 dependency/cycle operations

## Minimum manual delivery UI

The project's Delivery view now lists saved delivery records and supports
manual milestone, risk and approval creation. The editor exposes status,
owner wording, optional package/stage/work assignment and the five separate
date fields. Risk likelihood/consequence and approval authority/reference/
submission/determination dates have dedicated controls. Blank dates remain
unknown; clearing a date sends null. Status options match the record kind.
Saved records show their planning/review status, original proposal provenance
where present, direct excerpts and latest correction audit. A hold-point
proposal is labelled as a hold point in the view, although its stored delivery
kind is milestone.

The view inherits the existing list/detail layout and keeps its editor mounted
across project-view navigation. Events refresh saved records without replacing
unsaved entries. A version change disables save until the person compares the
latest record and explicitly retains their edits. Reconciliation carries only
changed fields onto the new version, including individual detail fields; it
does not overwrite another person's untouched authority or status. A changed
record kind requires reopening the editor. Patches omit unchanged assignments,
so historical links are not inadvertently resubmitted as new selections.
