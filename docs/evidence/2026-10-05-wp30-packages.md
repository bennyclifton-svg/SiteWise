# WP-30: packages and stages (in progress)

6 October follow-up: [mapped complexity suggestions](2026-10-06-package-complexity-suggestions.md)
now supplement baselines on GET packages, retaining matched reasons and draft
status. This supersedes the baseline-only implementation note below. Package
timing passes; the overall profile latency gate remains red.

Lane A. Outcome: services, works and supply packages organise commercial
responsibilities and editable delivery stages. API budget p50/p90 100/250 ms.
Responsibilities, pricing and tender issue are outside this package. No new
dependency or service is introduced.

Migration 017 adds tenant/project-scoped packages and stages, provenance,
optimistic versions, retirement, unique proposal provenance and live stage
labels. Works packages require a head-contract/trade scope; other kinds cannot
carry one. Novation is restricted to services packages. Verified status requires
an identified reviewer, time and basis. Package/stage identities use composite
foreign keys so another tenant or project cannot be referenced.

The rollback-only migration test passes using the actual schema and checks foreign
projects, wrong package ownership, invalid novation/scope combinations, duplicate
stage labels, unsupported verification and organisation deletion.

The loader now reads stages/substages, validates IDs and phases and includes
the file in the knowledge version. Procurement validation restricts novation
to services, works scope to works packages and stage choices to the catalogue.
User-created services packages receive four editable catalogue substages when
stages are omitted, with two pre/two post stages for novation and `none`
otherwise. An explicit empty list creates no stages. Caller-supplied stage
provenance is never trusted.

GET/POST packages and their store operations are implemented. Creation owns
package/stage identities, validates actor/project scope, writes provenance and
emits the packages revision/event atomically. API tests pass for creation,
listing, foreign tenants, invalid novation/unknown stages, provenance spoofing,
duplicate labels and rollback; no Jev calls occur. Knowledge and procurement
suites pass, as do focused store and HTTP package tests. The first store test
found a foreign-project FK error leaking through as a raw database error;
an explicit in-transaction ownership check now returns not-found instead.

PATCH package, POST stage and PATCH stage are now implemented. Project locking
and optimistic versions prevent concurrent edits from overwriting each other;
the concurrency test proves one success and one conflict for competing updates.
Stage renaming preserves identity. A package edit is rejected if it would make
an existing stage's pre/post novation phase invalid; the user can first edit the
stage phases. Package edits reset verification and record the editing actor.
Focused API tests cover stale versions, stage creation/renaming, invalid
novation changes and cross-project package IDs.

Package read/write paths are instrumented and have build-gated p50/p90 budgets
of 100/250 ms. The intake benchmark exercises package creation, package edits,
stage creation/edits and progressively larger lists. Benchmark evidence is
recorded in `bench/results/2026-10-05-wp30-crud.json`: full 184-file intake corpus,
two rounds, package reads p50/p90 2.9/4.7 ms (40 samples), package writes
2.2/2.8 ms (160 samples across the four write operations). Current user-path
gates pass on the development host; this is recorded-latency replay, not live
Jev or target-VPS release proof. The legacy baseline class/work-type vocabulary matches the
profile taxonomy; complexity additions still contain legacy field names that
must not be silently mapped or treated as known project facts.

Default baseline suggestions are implemented as a separate `suggestions` list
on GET packages, not saved packages or appointments. The catalogue is loaded
and hashed, validates class/work-type IDs and preserves legacy complexity rules
without applying unsupported mappings. Suggestions deduplicate across matching
work types and existing service-package names, retain catalogue draft status,
and always have proposed lifecycle/review status. A repeatable-read transaction
reads the package list and relevant profile rows consistently. Assumptions,
allowances, unknowns, superseded and unapplied values are excluded. Pure and
database eligibility tests pass, including removing suggestions when a work
type becomes explicitly unknown. The profile rows are scanned explicitly so
snake-case review/value-state columns cannot be lost during JSON decoding.

The updated diagnostic seeds an applied industrial/new-build profile and
asserts nine suggestions on every package read. With 40 package samples and
20 intake files per round, reads measured p50/p90 3.423/5.221 ms and writes
2.000/2.999 ms (`2026-10-05-wp30-defaults-diagnostic.json`). Current gates pass;
the reduced intake run is diagnostic evidence, not a full-corpus release run.

Discipline acceptance now creates a planned services package, editable stages
and the accepted decision in one project-locked transaction. The label is used
as the service title; no discipline ID is guessed from prose. Package and works
revision events are emitted atomically. Concurrent retries return one package,
and the HTTP accept route returns the created package for discipline kinds.
Synthetic fixture tests pass for concurrent retry, stale fingerprints, foreign
actors/projects and persistence after rebuilding. The HTTP path also passes.

Migration 017a extends decision targets using conditional generated FK anchors:
work targets must reference work items, and package targets must reference
packages, always in the same tenant/project. Actual-DDL tests reject a foreign
package and a package ID falsely tagged as a work item, and verify org deletion.

Package/stage PATCH supports retirement while preserving identities and history.
Retired records leave the active list; duplicate acceptance still returns an
existing package even if retired. Focused store/API/database suites pass.
Responsibility/cost/delivery/report blockers must be added when those reference
tables arrive; timing for discipline acceptance/retirement
remain outstanding. Catalogue defaults remain
draft; this work does not mark them reviewed or appoint anyone.

Package undo is implemented with the same conservative rule as work-item undo.
Acceptance records the created stages and their versions in its input snapshot.
Undo requires the original package version and the exact untouched stage set;
package edits, renamed/added/retired stages or other decision references block
it. Undo retires the package, preserves history and emits package/works revision
events. Reacceptance restores the same package and stage identities only when
the retained undo record matches the current versions. Older acceptances without
a stage snapshot fail closed. Store and HTTP tests cover undo/reacceptance,
edited-stage refusal and edited-package refusal. The store, HTTP and database
suites pass (`.tools/wp30-package-undo-tests.log`).
