question fast: **does SiteWise's built-in knowledge produce this consultant, cost line, program activity
or RFP scope item for this profile?**

## 0. How the pieces connect (read this first)

```
Profile header + determinants + conditions + flags   (hdr.*, det.*, hdr.cond.*, proj.*, proj.flag.*)
   │
   ├─ scope defaults ─► scope.<leaf> rows ─► work items (system + action)           §1
   │                                             │
   ├─ package rules ◄── scope rows ──────────────┘ ─► suggested consultants          §2
   │        └─ adopted on Cost Plan "prepare" ─► packages ─► fee lines               §3
   ├─ work items ─► cost elements ─► construction lines; starters ─► project lines    §3
   ├─ work type + route + planning ─► skeleton; work items + det.ncc_class ─► fragments §4
   ├─ package discipline id ─► RFP template; profile facts and flags ─► RFP rows      §5
   └─ work items + det.* ─► consequences / unforeseen ─► Implications only            §6
```

Three rules decide most outcomes, so learn them first:

1. **Only applied values count.** A profile row counts when its band is `user`, `amber` or `green`, it has a
   value, it is not unknown, cleared or superseded, its origin is not `assumption`, and its meaning is
   `stated` (`appliedWorkRow`, `internal/profile/existing.go`; the same rule is `appliedProgramRow` in
   `internal/store/program_prepare.go`). A value typed by the user is band `user`. A Jev reading needs at
   least amber; with green withheld everywhere (DISCOVERY.md §1.5) amber is the ceiling.
2. **Unknown is not false.** Program and works predicates are three-valued (`Truth`,
   `internal/knowledge/works_eval.go`; `evalPredicate`, `internal/knowledge/relevance.go`). A skeleton needs
   **true**. A fragment that is **unknown** is still added, as a conditional `If …:` row. An RFP row that is
   unknown becomes a decision, an option or an assumption, never a silent exclusion
   (`unknownState`, `internal/rfp/resolve.go`).
3. **`det.ncc_class` is never derived from the subclass.** Packages and fragments read the applied
   `det.ncc_class` only (`PackageBaselineFacts`, `internal/profile/package_defaults.go`;
   `readProgramGenInput`, `internal/store/program_prepare.go`). A project with no stated class gets every
   class variant (1a, 2, 7b, 9b) of each matching fragment as a conditional `If …:` row (verified, §9
   check 8). Set `det.ncc_class` in every scenario profile.

**Nothing in §1–§5 calls Jev.** All five generators are lookup and computation in Go (AGENTS.md "These
paths do not call Jev"; `internal/rfp/drivers.go` package comment; `internal/program/generate.go` header
comment "It is pure: no database, no Jev, no clock").

## 1. From profile to scope

### 1.1 The rule

`profile.Build` (`internal/profile/build.go`) reconciles the header first, then calls
`Catalog.ScopeDefaults(category, subclass, work_type)` (`internal/knowledge/profile.go`). The lookup, in order:

1. Work type empty → no defaults. Work type in `empty_work_types` (`refurb`, `remediation`, `advisory`;
   `knowledge/profile/scope_defaults.yaml empty_work_types`) → **no defaults**.
2. A `classes[]` entry whose `class` is the **subclass** and whose `work_type` matches.
3. Else that subclass's `work_type: new` entry.
4. Else the building class's `categories[]` list. The category is re-derived from the subclass by scanning
   all classes, **last match wins**. Subclass `other` exists in every class, so it always resolves to the
   infrastructure list (`categories[5]`, 10 systems), whatever the building class. Verified by running the
   Go (§9 check 8). This is a defect.

Only four subclasses have their own lists: `house` (new: 41 systems, `classes[0]`; extend: 16,
`classes[2]`), `townhouses` (new: 45, `classes[1]`), `warehouse` (new: 46, `classes[3]`; extend: 39,
`classes[4]`) and `apartments` (new: 62, `classes[5]`). Every other subclass uses its category list:
residential and mixed share the apartments list (YAML anchor `&id001`); commercial and institution share a
64-system list (`&id002`); industrial uses the warehouse list (`&id003`). Full lists and the per-subclass
table: [index/scope-defaults.md](index/scope-defaults.md).

Each default becomes a `scope.<leaf>` row valued `in` with band `suggested`, unless the user has set that row
`out` (`Build`, `withScope`). A scope row is also added for a system a read document states is included
(`sys.<leaf>.presence = included`, band amber, green or user), and for a system an applied works action names
(`sys.<leaf>.action` one of the eight actions) unless a document says it is not included (`withScope`). Words
in a read passage can suggest more rows (`implied_by` patterns such as `bathroom`, `kitchen`, `strip-out`,
`BASIX`; `ImpliedReadings`, `internal/profile/implied.go`; never overriding a user or document row,
`withImpliedScope`).

On refurb, remediation and advisory a document that only describes what already exists makes a
`sys.<leaf>.existing = present` row, not scope, unless an applied action or a `contractor` provider says it
is works (`existingPresence`, `withExistingSystems`, `internal/profile/existing.go`).

### 1.2 From scope rows to work items

`profile.ProposedWorks` (`internal/profile/works.go`) makes one coarse work item per `(part, system)` with a
`scope.<leaf> = in` row or an applied `included` presence row; deprecated systems are skipped. Its action is
the applied `sys.<leaf>.action` when there is one, else `works.DefaultAction`
(`internal/works/workitems.go`), which reads `knowledge/works/actions.yaml work_type_defaults`:

| work type | default action |
|---|---|
| new | `new` |
| extend | `new` |
| refurb | `alter` |
| remediation | `repair` |
| advisory | `investigate` |

(The frozen fallback `LegacyDefaultAction` gives the same mapping.) `syncProposedWorks`
(`internal/store/works.go`) writes them with `review_status: proposed`; it never overwrites a user-touched
or accepted item. A user scope choice (`PUT /projects/{id}/profile/scope`, `setWorkScope`,
`internal/store/works.go`) marks the item `accepted_for_planning`, which matters for the head contract (§2.4).

The eight actions and their meanings are `knowledge/works/actions.yaml actions` (`new`, `replace`,
`upgrade`, `alter`, `repair`, `remove`, `retain`, `investigate`). `existing_conditions` (`serviceable` …
`unknown`) is a work-item field only (`Catalog.ExistingConditions`, `internal/knowledge/works.go`,
validated by `PUT /profile/sys.<leaf>.condition`); no generator reads it.

### 1.3 Defaults by building class and work type

| class | subclasses with own list | new / extend list | refurb, remediation, advisory |
|---|---|---|---|
| residential | house, townhouses, apartments | house 41 / 16; townhouses 45 / 45; apartments 62 / 62; all others the residential category list (62) | empty |
| commercial | — | commercial category list (64) for both | empty |
| industrial | warehouse | warehouse 46 / 39; others the industrial list (46) | empty |
| institution | — | institution list (= commercial, 64) | empty |
| mixed | — | mixed list (= residential, 62) | empty |
| infrastructure | — | infrastructure list (10) | empty |
| any class | `other` | **infrastructure list (10)**, see §1.1 | empty |

The preset `typical_fit_out` (20 interiors and services systems, `scope_defaults.yaml presets[0]`) is
offered in the scope picker; it is never applied automatically (`Catalog.Presets`).

## 2. Procurement

### 2.1 Consultant suggestions

`procurement.SuggestedPackages` (`internal/procurement/defaults.go`) unions three rule sets from
`knowledge/works/package_defaults.yaml`. Inputs come from `profile.PackageBaselineFacts` and
`PackageComplexityFacts` (`internal/profile/package_defaults.go`), read by `packageOverview`
(`internal/store/packages.go`):

- **classes**: each applied `hdr.building_class` value, **plus** a category for each applied
  `det.ncc_class` value, through the subclasses whose taxonomy `ncc_class` is exactly that value. So `5` adds
  commercial, `6` commercial, `7a` and `7b` and `8` industrial, `9a` and `9b` institution, `2` and `1a` and
  `9c` residential, and `3` both residential and commercial. `1b`, `4` and `10a`–`10c` add nothing.
  **An apartment block with `det.ncc_class: 2,7a` becomes industrial too**, which brings Traffic, BCA,
  Access, Mechanical and Fire Services through `baselines[1]` (verified, §9 check 2).
- **workTypes**: each applied `hdr.work_type`.
- **scope**: every `scope.<system>` row valued `in`, **whatever its band** (suggested defaults count).
- **facts**: applied `det.*` and `hdr.cond.*` values; a field with two different applied values is dropped.

Rules, as "when … then":

| anchor | when | then |
|---|---|---|
| `baselines[0]` | work type new or extend, and no known class is infrastructure | Architect, Structural, Civil, Town Planner, Geotechnical, Surveyor, Certifier, Electrical, Hydraulic |
| `baselines[1]` | class industrial, commercial, institution or mixed; new or extend | Traffic, BCA, Access, Mechanical, Fire Services |
| `baselines[2]` | work type refurb (any class) | Architect, Certifier, Electrical, Hydraulic |
| `baselines[3]` | industrial, commercial, institution or mixed; refurb | BCA, Access, Mechanical, Fire Services |
| `baselines[4]` | commercial, institution or mixed; refurb | Interior Design |
| `baselines[5]` | infrastructure; new or extend | Civil, Structural, Geotechnical, Surveyor, Environmental, Town Planner |
| `scope_additions[0]` | any `vertical-transport.*` in scope | Vertical Transport |
| `scope_additions[1]` | `fire-active.sprinklers`, `.hydrants`, `.fire-water`, `.detection` or `.occupant-warning` in scope | Fire Services |
| `scope_additions[2]` | any `mechanical.*` | Mechanical |
| `scope_additions[3]` | any `hydraulic.*` | Hydraulic |
| `scope_additions[4]` | any `electrical.*` or `fire-active.emergency-lighting` | Electrical |
| `scope_additions[5]` | `access-egress.accessible-access`, `.accessible-facilities` or `.livable-housing` | Access |
| `complexity_additions[0]` | `hdr.cond.planning` da or ssd | Town Planner |
| `complexity_additions[1]` | `det.heritage_status` conservation_area, local_item or state_register | Heritage |
| `complexity_additions[2]` | field `contamination_level` | Environmental — **never fires**: no such determinant or condition |
| `complexity_additions[3]` | `hdr.cond.environmental_sensitivity` sensitive or protected_habitat | Ecology |
| `complexity_additions[4]` | `hdr.cond.environmental_sensitivity` aboriginal_heritage | Archaeology |
| `complexity_additions[5]` | `det.bal` any BAL value | Bushfire |
| `complexity_additions[6]` | field `flood_exposure` | Civil — **never fires**: no such field |
| `complexity_additions[7]` | `det.facade_type` complex | Facade |

Why two never fire: `packageFieldValue` (`internal/procurement/defaults.go`) accepts a value only when the
field is a live determinant or taxonomy condition and the value is one of its options. `contamination_level`
and `flood_exposure` are neither (`knowledge/determinants.yaml` has `potentially_contaminated_land` and
`flood_hazard`, both boolean). So **no site condition suggests an Environmental consultant or a flood
engineer outside infrastructure.**

Note also: there is **no baseline for `remediation` or `advisory`**, and their scope starts empty, so a
remediation or advisory project gets **no consultant suggestions at all** unless DA or SSD planning
(Town Planner), heritage, BAL, sensitivity or a complex facade apply, or scope is added (verified for T09,
§9 check 5).

Names are discipline labels (`data/intake/disciplines.json`), checked at load
(`loadPackageDefaults`, `internal/knowledge/package_defaults.go`); `procurement.ProposalDiscipline`
(`internal/procurement/discipline.go`) maps a suggestion key `default:services:<label>` to its id. A
consultant the user already has, removed or dismissed is not suggested again (`SuggestedPackages` `taken`,
`Dismissed`). Suggestions are transient until accepted (`POST /packages/proposed/accept`), adopted in bulk
(`POST /procurement/adopt`, `AdoptServiceSuggestions`, `internal/store/package_proposed.go`), or adopted by
the Cost Plan's prepare (§3). The resolved consultant list for every class, subclass and work type is in
[index/procurement.md](index/procurement.md).

### 2.2 Novation

- Every suggestion carries `Novation = DefaultNovation(route)` (`packageOverview`): `option` when
  `BuilderDesigns(route)` is true, else `no` (`internal/procurement/packages.go`).
- `BuilderDesigns(route)` is `route != "traditional"` (`internal/procurement/proposed.go`). **An unanswered
  route counts as design and construct**, so every consultant defaults to `option`;
  `RouteNeedsConfirm` flags `""`, `managing_contractor`, `alliance` and `ppp` for the user to confirm.
- A consultant row the user creates (`POST /procurement/rows`, `CreateDisciplinePackage`,
  `internal/store/packages.go`) takes the same default; a works package is always `no`. Only services can be
  novated, and `yes` is only ever the user's election (`ValidatePackage`). There is no novated-D&C route in
  the taxonomy (`knowledge/profile/taxonomy.yaml conditions.procurement_route`).

### 2.3 Package stages

`Store.defaultStages` (`internal/store/stage_sync.go`):

- **No program yet**: `procurement.DefaultStages` gives a services package the catalogue sub-stages in
  `knowledge/works/stages.yaml`: Concept design, Approval documentation, Construction documentation,
  Construction-stage inspections. On a novated or option package their sides are pre, pre, post, post.
- **Program exists**: `ProgramDefaultStages` gives the program's stages whose catalogue stage is a sub-stage,
  in program order and labelled as the program labels them. No skeleton contains
  `construction_stage_inspections`, so such a package gets at most three stages; `sk.new-traditional-cdc`
  has no construction documentation stage and `sk.refurb-traditional-cdc` no approval documentation stage,
  so those get two. **The order of calls changes package stages**: creating an RFP or a staged fee line
  creates the program first (`ensureProgram`, `internal/httpapi/stage_sync.go`, called from
  `postProcurementCreate` and others).
- Works and supply packages get no default stages.

### 2.4 Head contract and trade packages

- **Head contract** (`procurement.ProposeHeadContract`, `internal/procurement/proposed.go`): one proposal
  `proposed:works:head_contract` whose lines are the `gap` findings of `CheckGaps`
  (`internal/procurement/gaps.go`): "Carry out the works" for each missing `install`, "Design" for each
  missing `design` only when `BuilderDesigns(route)`, and "Protect and keep operating" for `retain` items.
  Investigations are left to the user. **Gaps are only checked on items `accepted_for_planning` or
  `verified`**; a proposed item reports `not_yet_accepted`. So with untouched default scope there is **no
  head contract proposal**. Accept items (for example `PUT /profile/scope`) to see one. No proposal when a
  trade package exists without a head contract.
- **Trade packages are never suggested.** They exist only when the user creates a row for a `trade.*`
  discipline (`POST /procurement/rows`; `procurement.DisciplinePackage`, `internal/procurement/discipline.go`:
  `trade.main_works` → works / head_contract, other `trade.*` → works / trade, `supplier.*` refused).
- **Fee-proposal packages**: a filed document cued as a proposal opens a submission and, if none exists, a
  package for its discipline (DISCOVERY.md §2.2, `proposals.Cue`, `EnsureProposalPackage`).

## 3. Cost plan

### 3.1 Sections

`costs.CostSections` (`internal/costs/totals.go`) puts each line, by its root line, in one of four sections:

| app section | shape.yaml `section` | which lines |
|---|---|---|
| `authority` | `fees_and_charges` | project-wide lines with category `authority_fees` |
| `consultants` | `consultants` | fee lines (`line_kind: fee`) |
| `construction` | `construction` | works lines (`line_kind: works`) |
| `contingency` | `contingency` | every other project-wide line: contingency, **escalation**, **exclusions** and owner-supply (`other`) |

### 3.2 Where each line comes from

`costs.Suggest` (`internal/costs/suggest.go`) builds structure only. `POST /projects/{id}/cost-plan/prepare`
(`prepareCostPlan`, `internal/httpapi/costs.go`) **first adopts every suggested consultant as a package**
(`AdoptServiceSuggestions`), then inserts the suggestions (`PrepareCostPlan`, `prepareCostLines`,
`internal/store/cost_suggest.go`), then spreads a stated budget and applies brief figures.

| line | comes from | rule |
|---|---|---|
| Fee line `F01…` per consultant | **packages** (every live services package, so the adopted suggestions of §2) | one per package, label = package title (`Suggest` fee loop) |
| Construction line per top-level system | **work items** (included, live, not group; any review status: `costSuggestInput` SQL) | a line when ≥1 work item is on the system or below; label `cost_label` or system label; codes 01–13 (`knowledge/costs/elements.yaml`) |
| Access-and-egress children | work items | `access-egress` is `itemised`: one child per child system with scope; `exits` and `livable-housing` are `costed: false` and get none |
| Steel and joinery split-outs | work items **plus a trade package** | `structure.steel` and `interiors.joinery` become child lines only when a live `trade.structural_steel` or `trade.joinery_kitchens` package exists (`elements.yaml overrides`) |
| Project-wide `P01…P07` | **profile** | `knowledge/costs/starter_lines.yaml`: design contingency, construction contingency, escalation, construction-certificate fees, service-authority fees, exclusions always; **DA fees and contributions** only when `hdr.cond.planning` is `da`, still suggested (marked "applicability unknown") when planning is unknown, dropped for cdc, exempt, ssd and the rest (`CostStarterHolds`, `internal/knowledge/cost_elements.go`) |
| "Owner supply: …" lines | profile | one per item parsed from `proj.owner_supply_stated` (`applyBriefFigures`, `internal/store/cost_budget.go`) |

The package each construction line is costed under is `mappedCostPackage`: a live works package with the
element's `trade` discipline (`site` → `trade.civil_works`, `fire-active` → `trade.fire_services`,
`mechanical` → `trade.mechanical`, `hydraulic` → `trade.hydraulic_plumbing`, `electrical` and
`comms-security` → `trade.electrical`; the rest `trade.main_works`), else the head contract, else the
planning label "Head contractor". Table: [index/cost-plan.md](index/cost-plan.md).

There are no SSD fees, no long-service levy, no s7.11/s7.12 contributions line separate from "DA fees and
contributions", no BASIX, no Sydney Water, no road-opening and no authority-specific line in the starters.

### 3.3 What is never priced

`Suggest` writes **no amount** on any line ("no amount assumed", "no amount or percentage assumed"). Amounts
appear only from:

1. a stated construction budget `proj.budget_stated` spread over the top-level construction lines by the
   first matching **budget split** (`spreadConstructionBudget`; `ChooseBudgetSplit`,
   `internal/knowledge/budget_splits.go`; `knowledge/costs/budget_splits.yaml`, `verified: false`). A split
   with `storeys_min` is skipped when `hdr.scale.storeys` is unknown. No split exists for remediation or
   advisory, or for industrial or institution refurb. `preliminaries` has no line and is spread pro rata.
2. `proj.contingency_stated` → the construction contingency line; owner-supply amounts; the exclusions
   label from `proj.exclusions_stated` (`applyBriefFigures`).
3. an award, which copies a firm's priced cells into fee lines (AGENTS.md; DISCOVERY.md §7).

So **fee lines, design contingency, escalation, authority fees and service-authority fees are never priced
by the app**, and there are no rates: `knowledge/costs/benchmarks.yaml` does not exist (it is optional,
`loadCostBenchmarks`, `internal/knowledge/cost_benchmarks.go`). A shape must name lines, never amounts.

## 4. Program

### 4.1 Inputs

`readProgramGenInput` (`internal/store/program_prepare.go`) feeds `program.Generate`
(`internal/program/generate.go`) with: applied `det.*` values (comma-separated for multi-choice), applied
work types (every part's), applied `hdr.cond.*`, `plan.*` values, `fact.*` dates, presence and existing
rows, **all included live work items (any review status)**, and live packages with their stages. A work item
also implies presence: new → present; replace, alter, upgrade, repair, retain → present and existing;
remove → existing, not present (`inferSystemState`).

### 4.2 Skeleton

`Catalog.MatchSkeleton` (`internal/knowledge/program.go`): among skeletons whose `applies_when` is **true**,
the one with most predicate terms (`PredicateTerms`) wins; a tie is noted (`CheckSkeletonTie`); none →
`sk.generic`. `knowledge/program/skeletons.yaml`:

| skeleton | applies when (all) | stage order |
|---|---|---|
| `sk.generic` | fallback | investigation, concept, approval docs, construction docs, approvals, procurement, construction, completion, defects |
| `sk.new-traditional-da` | new; traditional; da or planning_permit | … approval docs, approvals, construction docs, procurement … |
| `sk.new-traditional-cdc` | new; traditional; cdc or exempt | … approval docs, approvals, procurement … (no construction docs) |
| `sk.new-dc-da` | new; design_construct; da or planning_permit | … approvals, procurement, construction docs … |
| `sk.new-eci-da` | new; eci or managing_contractor; da or planning_permit | … concept, procurement, approval docs, approvals, construction docs … |
| `sk.refurb-traditional-da` | refurb; traditional; da or planning_permit | as new-traditional-da |
| `sk.refurb-traditional-cdc` | refurb; traditional; cdc or exempt | … concept, construction docs, approvals, procurement … |
| `sk.extend-traditional` | extend; traditional; da, cdc, exempt or planning_permit | as new-traditional-da |
| `sk.ssd-traditional` | new or extend; traditional; ssd | as new-traditional-da |
| `sk.ssd-dc` | new or extend; design_construct, eci or managing_contractor; ssd | as new-dc-da |

Falls back to `sk.generic`: **every remediation and advisory project**; refurb or extend under any route but
traditional (SSD aside); new under D&C with CDC or exempt; alliance and PPP; **`ref`, `modification`,
`planning_proposal` and `advice_only`** (so T20's REF school gets the generic skeleton, verified §9 check 7);
and any project whose route or pathway is unknown. Full matrix: [index/program-skeletons.md](index/program-skeletons.md).

### 4.3 Fragments

`gen.fragmentRows` (`internal/program/generate.go`), over `knowledge/program/fragments.yaml` (223 fragments,
56 with `scope: project`, 167 attached to work items; each names exactly one system):

- **Project fragments** (design, consent, tender, handover, investigation): added once when `applies_when`
  is true; added as `If <term>: …` rows when unknown; skipped when false.
- **Work-item fragments**: considered once per included work item on the fragment's system or below. The
  predicate is evaluated with that one item, so `work_action` reads its action. `retain` items bring nothing;
  `remove` items select only fragments whose predicate names `remove` (demolition, strip-out); `investigate`
  items select only investigation fragments that hold outright (`fr.investigate-*`), otherwise one generic
  Investigation row (`investigationRows`). True adds rows, unknown adds `If …` rows, false skips. A
  one-activity fragment takes the work item's title as its label (`instantiate`).
- Blank `det.flood_hazard` and `det.bushfire_prone_land` are treated as false (`assumeHazardsNo`), so
  `fr.flood-*` and `fr.bushfire-*` appear only when the profile says yes.

Suffix groups (counts; full table with ids, labels, stages, predicates and activity keys in
[index/program-fragments.md](index/program-fragments.md)):

| suffix | count | gate |
|---|---|---|
| `1a` | 46 | `det.ncc_class` 1a, mostly new or extend (process steps also refurb) |
| `1a-reno` | 8 | 1a and refurb |
| `2` | 49 | class 2 |
| `7b` | 24 | class 7b |
| `9b` | 35 | class 9b |
| `fitout` | 25 | classes 5, 6 or 9b (some 5 or 6 only) and refurb |
| `major` | 3 | switchboards (5, 6, 7b, 9b), utility supply (2, 7b, 9b), service connections (2, 5, 6, 7b, 9b) |
| `commercial` | 1 | gas for 2, 5, 6, 9b |
| unsuffixed | 32 | class-neutral items and process steps: consent, certificates, contract award, novation, handover, defects, the seven `fr.investigate-*`, lifts, fire-stopping, temporary power, erosion, tree protection, occupied protection, structure alterations, fit-out documentation |

The process steps that need a class (concept design, design development, approval documents, construction
documents, tender documents, tender period, tender evaluation, site establishment) exist only for 1a, 2, 7b,
9b and fit-out. Consent steps follow `hdr.cond.planning`: `fr.da-lodgement`, `fr.da-exhibition`,

## 5. RFPs

### 5.1 Template choice and resolution

- A services package's RFP uses the template whose `discipline_ids` contain the package's `discipline_id`
  (`Catalog.RFPForDiscipline`, `internal/knowledge/rfp.go`; `reportTemplateFor`,
  `internal/store/report_rfp.go`). A title alone never selects one (`title_aliases` only suggest). **No
  match → the generic `tpl.rfp-capex` report** (`reportTemplate`, `internal/store/reports.go`). Works
  packages get an RFT (`tpl.rft`).
- Facts come from the report snapshot (`rfp.Drivers`, `internal/rfp/drivers.go`): `work_type`, `pathway`
  (`hdr.cond.planning`), `procurement` (`hdr.cond.procurement_route`), `state`, `regulated_design`
  (`proj.regulated_design`), scale numbers (`hdr.scale.*`), `budget` (the cost plan's, else
  `proj.budget_stated`), the package's `novation`, each part's NCC classes, flags (§6.3–6.5).
- Grammar, three-valued: a `when` is a list of clauses (any true → true); keys in a clause all hold
  (`eval`, `clause`, `driver`, `internal/rfp/resolve.go`). Keys: `work_type`, `pathway`, `procurement`,
  `novation`, `state`, `regulated_design`, `class` (any part), `only_class` (every part), `flag`, `stage`,
  `stage_included`, `element`, `module`, `scale`, `budget_over`, `site_area_over`, `gfa_over`,
  `parking_over`.
- Unknowns (`unknownState`): `suggest` false → exclude, else ask; conflict → ask; `if_unknown: option` →
  priced option with the printed assumption; `if_unknown: include` → included; otherwise ask. Stages before
  the boundary start are excluded, after its end priced as options (`resolveStages`). `default: option`
  stages stay options unless `include_when` holds.
- Scale (`resolveScale`): complex when any `scale.complex` clause is true; simple when all false; **assumed
  simple with a check** when any is unknown. Only `service_level` positions follow scale.
- Modules (`knowledge/rfp/modules.yaml`): `existing_building` (refurb, extend, remediation or the flag),
  `live_site`, `remediation`, `advisory` (work type advisory or pathway advice_only), `mixed_use`,
  `staged`, `house` (every part only 1a, 1b, 10a, 10b and at least one 1a or 1b), `beyond_house` (class 2–9c;
  `if_unknown: include`). A row naming a module applies only while the module is on.
- Shared returnables R1 Fee by stage … R9 Reimbursables, terms, fields and evaluation weights (price 40,
  experience 20, team 20, methodology 10, compliance 10) are in `knowledge/rfp/skeleton.yaml`.
- Blocking checks to expect: `pathway_unsupported` when `hdr.cond.planning` is in a template's
  `unsupported_pathways` (`checkPathway`); `fact:budget` when a template's `required_facts` has budget and
  none is set (`checkRequiredFacts`); client-owned allowance counts with no default; and drafting refuses to
  run while documents are pending or failed or the profile is stale (`ReadingIncomplete`,
  `internal/reports/assemble.go`).

## 7. Running the generators without Jev

Yes: every generator runs from a hand-entered profile with no Jev call. Two ways.

### 7.1 Pure Go, no database (verified, §9)

The generators are plain functions over a loaded catalogue. A small `package main` inside the module (the
harness can live under `testing/synthetic/harness/`, which may import `sitewise/internal/...`), or a file
outside the repo run with `go run -overlay overlay.json ./internal/<virtual dir>`, can call, in order:

```go
cat, _ := knowledge.Load("knowledge")                                   // internal/knowledge/load.go
rows := profile.Build(profile.Input{Parts: parts, User: userValues}, cat) // internal/profile/build.go
items := profile.ProposedWorks(projectID, rows, parts, cat)               // internal/profile/works.go
scoped := profile.ProjectWorkScope(rows, items)
classes, workTypes, scope := profile.PackageBaselineFacts(cat, scoped)    // internal/profile/package_defaults.go
facts := profile.PackageComplexityFacts(scoped)
sugs := procurement.SuggestedPackages(cat, procurement.SuggestionInputs{Classes: classes, WorkTypes: workTypes, Scope: scope, Facts: facts})
lines := costs.Suggest(costs.SuggestInput{Catalog: cat, Packages: pkgs, Works: works, Values: map[string]string{"hdr.cond.planning": "da"}})
split, _, ok := cat.ChooseBudgetSplit(knowledge.SplitProfile{Class: "residential", Subclass: "house", WorkTypes: []string{"new"}})
plan, _ := program.Generate(cat, program.GenInput{Values: dets, WorkTypes: []string{"new"}, Conditions: conds, WorkItems: gitems, Packages: gpkgs})
d, _ := cat.RFPForDiscipline("consultant.structural"); sk, _ := cat.RFPSkeleton()
resolved := rfp.Resolve(d, sk, rfp.DriverSet{Facts: ..., Parts: ...}, rfp.Settings{})   // or rfp.Drivers(reports.Snapshot, sk)
gaps, _ := procurement.CheckGaps(items, packages, assignments, cat); head := procurement.ProposeHeadContract(gaps, items, packages, route)
props, _ := works.EvaluateProposals(cat, works.ProposalInput{...})       // Implications
```

User values are `profile.UserValue{Scope: cat.KeyScope(key) or "project", PartID: wholePartID, Key, Value,
State: "set"}` on a part `{Kind: "whole"}`. This is exactly what §9 ran. Existing Go test helpers to copy
from: `chenHouse()` (`internal/program/house_defaults_test.go`), `testCatalog`
(`internal/program/generate_test.go`), the procurement default tests (`internal/procurement/defaults_test.go`),
`TestCostSuggestionsScopeAndSuppression` (`internal/costs/suggest_test.go`).

**RFP selection already has an answer-key format.** `data/eval/rfp/answer-keys/*.yaml` (126 scenarios plus a
README) give facts, flags, parts, settings and expectations (`stages_include`, `stages_option`,
`stages_absent`, `stages_ask`, `positions` I/O/X/ask/absent, `party`, `blocking`, `scale`), run by
`TestSelectionAnswerKeys` (`internal/rfp/answerkey_test.go`, scenario struct in `internal/rfp/fixtures_test.go`).
Wording snapshots are in `internal/rfp/testdata/<case>/<discipline>.md`. A synthetic RFP expectation can be
written in that format.

### 7.2 Through the local API (closest to a user)

All under `/api` (`mux.Handle("/api/", …)`, `internal/httpapi/server.go`); every write needs an `Origin`
header equal to the server's public origin (`originOK`, `internal/httpapi/projects.go`). None of these calls
Jev:

1. `GET /dev/login` (dev server only) → session cookie (`devLogin`, `internal/httpapi/devlogin.go`).
2. `POST /api/projects {"name": …}` → `{"id": …}` (`createProject`).
3. `PUT /api/projects/{id}/profile/{key}` `{"value": "…", "origin": "user"}` for each key: `hdr.building_class`,
   `hdr.subclass`, `hdr.work_type`, `hdr.cond.<key>`, `det.<id>` (only determinants with a `profile_group`;
   multi-choice comma-separated, for example `1a,10a`), `fact.<id>`, `proj.<detail>`, `proj.flag.<key>`
   (`yes`/`no`), `plan.<key>`, `hdr.scale.<field>`, and `sys.<leaf>.presence`, `.existing`, `.provider`,
   `.condition` or `.note` (`putProfileValue`, `validProfileValue`, `internal/httpapi/profile.go`). A work
   item's action is not a profile key: set it with `PATCH /works/{wi}` (step 4). Each write rebuilds the profile
   projection and the proposed work items (`SetUserValue` → `finishProfileWriteLocked`,
   `internal/store/revisions.go` → `rebuildProfileProjectionLocked`, `internal/store/profile.go`).
4. Optional scope: `PUT /api/projects/{id}/profile/scope {"systems": {"<leaf>": "in"|"out"}}` (accepts the
   items for planning); `POST /api/projects/{id}/works`, `PATCH /api/projects/{id}/works/{wi}` (action,
   inclusion, layout change).
5. Snapshots: `GET /api/projects/{id}/profile`, `GET /api/projects/{id}/works`,
   `GET /api/projects/{id}/packages` (suggestions with novation, route, gaps, proposed head contract),
   `GET /api/projects/{id}/proposals?show=all` (Implications).
6. `POST /api/projects/{id}/program/prepare {"surface": "program"}` → generated program (idempotent:
   creates once, `PrepareProgram`). Prepare the program **before** adopting packages if you want program
   stages on them (§2.3).
7. `POST /api/projects/{id}/cost-plan/prepare {}` → adopts suggested consultants, then the cost plan with
   totals (`prepareCostPlan`). Or `POST /api/projects/{id}/procurement/adopt` alone.
8. `POST /api/projects/{id}/procurement/create {"proposal_key": "default:services:Structural"}` or
   `{"package_id": …}` → package plus RFP report and draft (`postProcurementCreate`,
   `internal/httpapi/procurement.go`); then `GET /api/reports/{r}` for the sections.
9. `GET /api/projects/{id}/program`, `GET /api/projects/{id}/cost-plan`.

**Unverified**: the exact JSON field names of every snapshot response; read them from a live call before
writing the scorer.

### 7.3 Existing `cmd/` tools

None of them runs the generators from a hand-entered profile. `cmd/works-eval` scores an exported work-item
snapshot against a key and never calls Jev, but it needs a private corpus manifest
(`cmd/works-eval/main.go`). `cmd/program-eval`, `cmd/profile-eval`, `cmd/proposal-eval`, `cmd/invoice-eval`
and `cmd/intake-eval` calibrate Jev readings (live or replay). `cmd/proposal-eval -schedule <discipline>`
prints a discipline's default fee schedule (comment in `cmd/proposal-eval/main.go`; **unverified** whether it
needs the private key). `internal/program/cmd/genfixture` writes a synthetic engine fixture only.

**Recommendation for the harness:** compare shapes with §7.1 (fast, deterministic, no server, no Jev); use
§7.2 only for end-to-end runs that include filing and reading.

## 10. Validator vocabulary (`testing/synthetic/tools/validate_shape.py`)

It checks ids against the repo, so map every item to one of these:

- `hdr.building_class`, `hdr.subclass` (must belong to the class), `hdr.work_type`
  (`knowledge/profile/taxonomy.yaml`); `hdr.scale.*` any; `hdr.cond.<key>` with an option or user option.
- `det.<id>`: any id in `knowledge/determinants.yaml`, including ones the app cannot set (no
  `profile_group`, for example `commercial_kitchen`, `groundwater_above_excavation`).
- `fact.<id>` (`project_facts.yaml`); `proj.<key>` and `site.<key>` (`project_details.yaml` keys: client, lga,
  zone, program, target dates, budget_stated, contingency_stated, owner_supply_stated, exclusions_stated,
  regulated_design, preliminary_estimate, sustainability, address, lot …).
- `flag.<key>`: **only** the 32 keys in `knowledge/profile/flag_readings.yaml`. The app stores these as
  `proj.flag.<key>`. Flags read from determinants (`heritage`, `bushfire`, `flood`, `contamination`,
  `acid_sulfate`, `existing_building`) must be written as their `det.*` key, `live_operations` as
  `hdr.cond.operational_constraints`. The client-decision flags (`hyd_*`, `elec_*`, `mech_*`, `fs_*`,
  `geotech_*`, `survey_*`, `bca_*`, `cost_*`, `access_*`, `waste_*`, `landscape_*`, `arborist_impact_report`,
  `objections`, `super_flat_floor`, `contract_admin` and others) are **rejected**: record them in `gaps` or
  prose. `plan.*` keys are rejected too.
- Systems: any id in `knowledge/systems.yaml` or `clusters/*/systems.yaml` (the validator accepts the
  deprecated `fire-passive.bushfire-construction`; use `envelope.bushfire-construction`). Actions: the eight.
- Disciplines: `data/intake/disciplines.json` ids or `none`. RFP `template`: one of the 18 ids above.
  Fragments: `fragments.yaml` ids. Skeleton: `skeletons.yaml` id or `missing`.
- `cost_plan[].section`: `fees_and_charges` (the app's `authority`), `consultants`, `construction`,
  `contingency` (escalation and exclusions live here in the app).
- `built_in: yes|partial` needs a `source` that is an existing repo path, optionally followed by a space or
  `#` and an anchor.
